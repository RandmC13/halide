# Task 2.4: GPU, service and shared memory — findings

Scope: `device.py`, `gpu_service.py`, `shared_frames.py`, `io/exiftool.py`, the GPU parts of
`processing.py` / `batch/orchestrator.py`, `gui/proof_window.py`'s use of the service,
`cli/_device_args.py`, `cli/commands/gpu_cmd.py`.

How it was reproduced without a GPU: `.review/scratch/2.4/cli_service.py` runs the **real CLI**
with `resolve_device` returning a fake "gpu" `ComputeDevice` and `orchestrator._SERVICE_KIND =
"cpu"`, so `halide batch` starts a real spawned service process, real forkserver workers, real
`/dev/shm` frames and real exiftool sessions. Only the arithmetic runs in numpy instead of CuPy.
Signal tests (`ctrlc.sh`, `killworker.sh`, `killgroup.sh`, `hupgroup.sh`) run it under `setsid` and
signal the group or single processes. Synthetic 700x1000 scans; all outputs deleted afterwards.

Checked and found sound (no finding): Ctrl-C to the process group mid-batch (clean: "Cancelled —
3/16 frames processed", no processes, no `/dev/shm` segments, no socket left); SIGKILL of one
worker holding a frame (the sweep removes it; the rest of the batch gets the documented "worker
process crashed" error); SIGTERM to the parent only (the service sees EOF and exits, and the
resource tracker removes the segments); the authkey (32 random bytes) and socket placement (inside
the parent's own `pymp-*` directory, mode 0700, so another user can't reach it and a second halide
run can't collide with it); per-batch `/dev/shm` prefixes (pid plus a random token, so two
concurrent runs never sweep each other's frames); the exiftool pipe (stderr is merged into stdout
and drained by a reader thread, so there's no deadlock risk); exiftool's `{status=N}` parsing on
success, a missing source, a missing destination and a read-only folder (all correct against
exiftool 13.50); and `HALIDE_DEVICE` / `--device` parsing (case, spaces, an empty value).

### 2.4-1: An interrupted service request leaves the connection out of step, so the next frame gets the previous frame's reply and its undeveloped negative is written out
- Severity: S2 (the mechanism is an S1: a raw negative written silently under a plausible
  provenance. The trigger is narrow: Ctrl-C, or any BaseException, landing inside a request while
  that worker still has another job queued)
- Where: src/halide/gpu_service.py:168-188 (`ServiceClient._request`)
- Evidence: `_request` marks the client dead only for `(OSError, EOFError, TimeoutError)`:
  ```python
  conn.send(message)
  if not conn.poll(self._timeout): ...
  status, payload = conn.recv()
  except (OSError, EOFError, TimeoutError) as exc:
      raise self._give_up(...)
  ```
  A `KeyboardInterrupt` raised during `poll`/`recv` leaves `_dead = None` with a reply still owed on
  the connection. `.review/scratch/2.4/desync.py` uses a real spawned service whose develop takes
  1.5 s, interrupts request A after 0.3 s with SIGALRM→KeyboardInterrupt, then sends request B:
  ```
  request A interrupted; client dead? None
  reply for B == A's result: True
  reply for B == B's result: False
  B's pixels developed? False | still the raw negative? True
  ```
  In a batch, `process_scan` would then write B's shared frame (still the decoded negative, or
  half-developed by the service racing it) to B's output path, with A's tone/profile as its
  provenance. Why it's reachable: Python 3.14's `ProcessPoolExecutor` worker catches
  `BaseException` from a job and carries on with the next queued call item
  (`concurrent/futures/process.py::_process_worker`). After Ctrl-C, `_run_pool` waits up to 10 s
  for workers (`_wait_for_exit`), with the service still alive, so a job that was already in the
  call queue (at pool start-up, or just after a completion) runs on the desynchronised client. A
  full-batch reproduction wasn't attempted (the window is milliseconds wide), so this is
  confirmed at the client level and likely in a batch.
- Suggestion: in `_request`, catch `BaseException` around send/poll/recv, call `_give_up(...,
  host_touched=True)`, and re-raise the original exception. That's the same "any doubt means
  dead" rule the timeout already follows. Add a regression test modelled on desync.py. S.
- Confidence: confirmed (client level); likely (whole batch)

### 2.4-2: Closing the terminal (SIGHUP) or a whole-group kill mid-batch leaves shared frames in /dev/shm (RAM) until reboot
- Severity: S2
- Where: src/halide/shared_frames.py (cleanup relies on `sweep` in the parent or on the resource
  tracker); src/halide/batch/orchestrator.py:540-556 and `_run_pool`'s `finally`
- Evidence: `hupgroup.sh` sends `kill -HUP -- -<pgid>` to a service-mode `halide batch` (what closing
  the terminal window does to the foreground job):
  ```
  shm before: halide-19361-5aafe945-2e7234167abf465f8f74f90a03b33524
  exit=129
  --- later:
  -rw------- 1 agent agent 8400000 Sep 28 09:55 halide-19361-5aafe945-2e7234...
  ```
  `killgroup.sh` (SIGKILL to the group, which is what systemd-oomd does to a whole scope under
  memory pressure) leaves both workers' segments behind the same way. All three cleanup paths die
  together here: the parent (`sweep`), the worker (`new_frame`'s `finally`) and the shared
  `resource_tracker`, which ignores SIGINT and SIGTERM but not SIGHUP or SIGKILL. Nothing later
  removes a `halide-<pid>-…` segment whose owner is dead: `sweep` only matches its own batch's
  prefix. On the user's machine a real frame is ~182 MiB, and 6 service-mode workers hold one each,
  so each such exit loses ~1 GiB of RAM (`/dev/shm` is tmpfs) until reboot. That memory also
  shrinks the `/dev/shm` cap of every later batch. SIGTERM to the parent alone, and Ctrl-C, were
  both clean (see the header).
- Suggestion: at the start of `batch_compute`, sweep `halide-<pid>-*` segments whose `<pid>` is no
  longer running. The names already carry the pid, so this is a few lines in `shared_frames`,
  Linux only, like `sweep`. Optionally also handle SIGHUP in the parent like SIGINT. S.
- Confidence: confirmed

### 2.4-3: After the service dies, every remaining frame gets its own identical, technical warning
- Severity: S3
- Where: src/halide/gpu_service.py:170-171 (a dead client re-raises the same reason on every frame);
  src/halide/processing.py:456-458; cli/commands/batch_cmd.py:366-368 (one line per result);
  pinned by tests/unit/test_orchestrator.py:820 (`test_when_the_service_dies_mid_batch…`)
- Evidence: `.review/scratch/2.4/kill_service.py` SIGKILLs the service after 2 of 12 frames:
  ```
  f02.tif ok | the GPU service stopped responding (BrokenPipeError: [Errno 32] Broken pipe) — developed this frame on the CPU instead
  f03.tif ok | the GPU service stopped responding (BrokenPipeError: [Errno 32] Broken pipe) — developed this frame on the CPU instead
  … (the same line for f04 … f11)
  ```
  For the 37-frame roll in the task description, that would be ~35 identical ⚠ lines at the end of
  the run. The text is also a Python exception (`BrokenPipeError: [Errno 32]`), and "stopped
  responding" is repeated for frames that never contacted the service at all. Per-worker GPU mode
  does the same (`_start_on_device` adds "the GPU failed (…)" to every frame of a worker whose GPU
  is unusable), and so does the "no room in shared memory" path (2.4-8).
- Suggestion: report a device or service failure once per batch in words ("The GPU service
  stopped after frame 3 — the remaining 34 frames were developed on the CPU (same result within the
  GPU tolerance)"). Keep per-frame detail only for failures that really are per frame (out of GPU
  memory on one big frame). Simplest route: a `kind` on the warning, so `batch_cmd`/`print_cmd`/
  `export_cmd` and the proof window can group repeats. M (touches the test above).
- Confidence: confirmed

### 2.4-4: A bad input file is reported as "the GPU failed", then fails again on the CPU
- Severity: S3
- Where: src/halide/processing.py:473-493 (`run_device_job` catches every `Exception`),
  src/halide/gpu_service.py:360-361 (`_handle`), src/halide/processing.py:459-462 (wording)
- Evidence: `.review/scratch/2.4/odd_inputs.py`, same batch on CPU and in service mode:
  ```
  cpu     rgba.tif | err: matmul: … (size 3 is different from 4) | warn: None
  service rgba.tif | err: matmul: … (size 3 is different from 4) | warn: the GPU failed (ValueError: matmul: … (size 3 is different from 4)) — developed this frame on the CPU instead
  ```
  (a grayscale file behaves the same way). The device path treats any exception as a GPU fault,
  so a problem with the file itself is first blamed on the GPU and then reported a second time as
  the real error. The in-process GPU path (`invert --device gpu`, per-worker mode) does the same,
  because `run_device_job` is shared. (The raw numpy `matmul` message for an RGBA or gray scan is an
  input-validation gap for 2.1/2.3; noted here only for the misattribution.)
- Suggestion: validate shape and channels before handing the frame to any device (the check
  belongs in `_read_scan`, and then fixes the numpy message too). Or narrow what counts as a
  device failure to CuPy/CUDA errors plus MemoryError, and re-raise the rest unchanged. S.
- Confidence: confirmed

### 2.4-5: The hung-exiftool safety net ends in a one-shot call with no timeout, so a hanging exiftool still hangs the batch
- Severity: S3
- Where: src/halide/io/exiftool.py:307-313 (`_one_shot`), 339-349 (`execute`)
- Evidence: after two session timeouts, `execute` runs `subprocess.run([EXECUTABLE, *args],
  check=True, …)` with no `timeout`. With a fake `exiftool` that only sleeps, and
  `DEFAULT_TIMEOUT = 1.0`:
  ```
  after 10.0s: finished=False (session timeouts 2 x 1 s, then the one-shot call has no timeout)
  ```
  CLAUDE.md:430 says "if that fails too, the process goes one-shot … so a broken exiftool never
  hangs the batch". That holds for an exiftool that *dies*, but not for one that *hangs* on a file,
  for example on a stalled network share. Such a hang then blocks that worker for good (and so the
  batch's end), after already spending 2 × 120 s.
- Suggestion: give `_one_shot` the same `DEFAULT_TIMEOUT` (`subprocess.run(timeout=…)`), and on
  `TimeoutExpired` remove `<file>_exiftool_tmp` and raise `ExifToolError("exiftool didn't finish
  within … s")`. S.
- Confidence: confirmed

### 2.4-6: A broken CuPy install falls back to the CPU silently, and `halide gpu` prints the word "None" as the reason
- Severity: S3
- Where: src/halide/device.py:86-89; src/halide/cli/commands/gpu_cmd.py:56-57, 87
- Evidence: `resolve_device("auto")` treats any `ImportError` as "CuPy not installed" (`reason = None
  if isinstance(exc, ImportError)`). CuPy reports a broken install (for example "CuPy failed to
  load libnvrtc…") as an `ImportError`, while `gpu_support_installed()` (`find_spec`) still says
  it's installed. Simulated:
  ```
  auto -> ComputeDevice(kind='cpu', …, fallback_reason=None)
  --- halide gpu:
  GPU support is installed, but the card isn't usable right now.
      None
  --- halide gpu --install:
  It isn't usable right now: None
  --- run sheet: hint None | warning None
  ```
  So the run sheet says "Compute CPU" with no reason and no hint, and the one command meant to
  explain things prints "None".
- Suggestion: set `fallback_reason` to `str(exc)` for an `ImportError` whenever
  `gpu_support_installed()` is True; only a missing module means "not installed". Guard the
  `gpu_cmd` prints against `None`. S.
- Confidence: confirmed (simulated with a patched `_probe_gpu`; no real broken CuPy here)

### 2.4-7: The batch parent creates a CUDA context of its own just to probe the GPU, and holds it for the whole batch; CLAUDE.md says CUDA only exists in the service
- Severity: S3
- Where: src/halide/cli/commands/batch_cmd.py:298 (`resolve_device_arg` → `device._probe_gpu`: `import
  cupy` and a real kernel); the same for print/export/calibrate; CLAUDE.md:645
- Evidence: `_probe_gpu` runs `(cupy.arange(4, …) ** 1.5).sum().item()` in the parent, which creates
  a CUDA context and loads CuPy's and CUDA's host libraries. They stay loaded while the pool and
  the service run. CLAUDE.md measured those libraries at ~840 MiB of host RAM per process ("GPU
  worker ~1.2 GiB vs CPU worker ~0.4 GiB"), and RAM is the stated limit on the user's machine.
  `test_gpu_service_keeps_cupy_out_of_the_parent` only covers `running_service` called directly,
  not the CLI, which has already imported CuPy by then. The worker count isn't wrong (psutil's
  `available` is read after the probe), but the parent likely costs ~one worker's worth of RAM.
  Not measured: there is no GPU and no CuPy here.
- Suggestion: for commands that go through `batch_compute`, let the service do the probe (its
  "ready" message can carry name, free and total memory), or probe in a short-lived subprocess.
  Measure parent RSS on the user's RTX 3070 before and after. M.
- Confidence: likely

### 2.4-8: Fallback and "service not used" wording differs between paths, and some messages show raw error text
- Severity: S4
- Where: src/halide/processing.py:287-288, 449-462; src/halide/cli/_run_sheet.py:64-65;
  src/halide/gui/proof_window.py:109-110; src/halide/batch/orchestrator.py:733 (`_print_worker`),
  processing.py:635-638
- Evidence (all reproduced except the GUI line, which was read):
  - Run sheet: `GPU service not used: shared memory (/dev/shm) has 30 MiB free, too little for one 34
    MiB frame — each worker uses the GPU itself instead, which takes more memory per worker`
  - Proof window: `GPU service not used (<reason>) — each worker uses the GPU itself instead`
    (parentheses instead of a colon, and the second half is dropped).
  - Shared-memory fallback repeats itself and shows bytes and errno: `f01.tif: no room in shared memory
    for the GPU service (no room for a 36000000-byte shared-memory segment: [Errno 28] No space left
    on device) — developed this frame on the CPU instead`
  - Service loss: `the GPU service stopped responding (BrokenPipeError: [Errno 32] Broken pipe)`
  - `halide print` falls back with "developed this frame on the CPU instead" (`_run_on_service(…,

  - `resolve_device("gpu")` says "Run 'halide gpu --install' to check/fix it" for a GPU that is

- Suggestion: one helper for "service not used" (shared by the run sheet and the proof window); an

### 2.4-9: Ctrl-C in the first second of a batch prints pages of forkserver tracebacks instead of "Cancelled"
- Severity: S5 (overlaps 2.3's Ctrl-C item; noted here because it was found in the service-mode runs)
- Where: src/halide/batch/orchestrator.py `_run_pool` (the pool start-up: `_pool_context` preloads
  `colour`/scipy)
- Evidence: `ctrlc.sh 0.6 INT group` (3 runs out of 3): the log contains `Traceback … forkserver.py
  … main … colour/__init__.py … scipy/special …` from the forkserver (interrupted during its
  preload) and, in the parent, `ConnectionResetError` from `forkserver.connect_to_new_process`.
  There is no "Cancelled — 0/N" line. From 1.0 s onwards the same test gives the clean "Cancelled —
  0/24 frames processed."
- Suggestion: treat `KeyboardInterrupt`/`BrokenProcessPool`/`ConnectionResetError` raised while
  the pool is being created as a cancellation. Optionally ignore SIGINT in the forkserver during
  its preload (the parent owns cancellation, as the service already does). S.
- Confidence: confirmed

### 2.4-10: `halide gpu --install` says how to remove the install, but the command leaves most of the ~1 GB behind; pipx installs lose it on reinstall
- Severity: S5
- Where: src/halide/cli/commands/gpu_cmd.py:115-121, 132
- Evidence: it installs `cupy-cuda13x[ctk]` and says "about 1 GB, mostly NVIDIA's CUDA libraries.
  Remove it later with: python -m pip uninstall cupy-cuda13x". The `[ctk]` extra pulls in the
  NVIDIA CUDA wheels as separate distributions, which `pip uninstall cupy-cuda13x` doesn't remove.
  Separately, in a pipx venv pip is importable (pipx's shared libraries), so the automatic path
  runs `python -m pip install` there directly rather than `pipx inject`. pipx doesn't record the
  package, and `pipx reinstall(-all)` (needed after every Python upgrade on a rolling distribution
  like CachyOS) drops it quietly. The GPU hint does reappear on the run sheet afterwards.
- Suggestion: name the NVIDIA packages in the uninstall line (or say "the CUDA libraries stay
  installed"); when `sys.prefix` is inside a pipx venv, run or print `pipx inject halide …`. S.
- Confidence: likely (not installed: CuPy must not be installed in this sandbox)

### 2.4-11: Shared-frame names are 55 characters, over macOS's 31-character POSIX shm limit
- Severity: S5 (latent: the service needs CUDA, which macOS doesn't have, so nothing reaches it today)
- Where: src/halide/shared_frames.py:110, 195
- Evidence: `/halide-99999-8998d5a3-bb51fcaf7dee4c67a3d10796a67ad83e` is 55 characters. The stdlib
  keeps its own names at 14 characters for exactly this reason
  (`multiprocessing/shared_memory.py:30`, `_SHM_SAFE_NAME_LENGTH = 14`, "FreeBSD (and perhaps other
  BSDs) limit names to 14 characters"; macOS's `PSHMNAMLEN` is 31). On macOS `shm_open` would fail
  with ENAMETOOLONG, and every frame would get the misleading "no room in shared memory" warning.
  Other macOS points, checked by reading: the pool uses forkserver (available there) and the
  service uses spawn; exiftool stays one-shot (`_KEPT_OPEN_SUPPORTED`); `sweep` and the `/dev/shm`
  cap are no-ops. Those are all fine.
- Suggestion: a shorter scheme, e.g. `hl<pid base36><4 hex><6 hex>` (≤ 20 characters), or a comment
  recording the limit, so a future non-CUDA backend doesn't trip on it. S.
- Confidence: likely (read; no macOS here)

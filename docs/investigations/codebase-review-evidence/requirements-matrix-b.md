## Findings

### 3b-1: `/dev/shm` posix semaphores leak across test files, causing spurious teardown errors when run together
- Severity: S5
- Where: tests/unit/test_gpu_service.py:120 (`_no_leftover_segments` autouse fixture), interacting with `tests/unit/test_orchestrator.py`'s GPU-service tests (both use real `ProcessPoolExecutor`/forkserver pools)
- Evidence: Running the 11 device/orchestrator/gpu test files together produces 3 errors in `test_gpu_service.py` (`test_cpu_service_develops_bit_identical_to_direct_cpu_call[print]`, `test_leaving_running_service_stops_it_with_a_request_in_flight`, `test_first_connect_to_a_frozen_service_is_bounded`), each failing the fixture's `assert after - before == set()` because generic `sem.mp-*` posix semaphores (CPython's own multiprocessing resource-tracker objects, not halide's named `SharedFrame` segments) are left in `/dev/shm` by earlier tests in the same session. Running `tests/unit/test_gpu_service.py` alone: 35 passed, 0 errors. `ls /dev/shm` after the combined run showed 15 leftover `sem.mp-*` entries.
- Requirement: R-076 (test hygiene / isolation), tangential to R-084's `/dev/shm` sizing
- Suggestion: either scope `_no_leftover_segments` to ignore generic `sem.mp-*` multiprocessing semaphores (only assert on halide's own named prefix), or have the fixture clean up `sem.mp-*` leftovers itself before asserting so cross-file pollution doesn't fail an unrelated test. (S)
- Confidence: confirmed

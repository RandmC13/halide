### 5-5: `HALIDE_NO_COMPLETION=1` does not disable "it all" — `detect_shell()`'s psutil probe still runs on every invocation, costing ~20-30 ms unconditionally
- Severity: S3 UX friction / minor correctness-of-contract (documented behavior not met)
- Where: `src/halide/cli/completion.py:438-447` (`maybe_install_completion`), called from
  `src/halide/cli/main.py:141-144` (`run_cli`, the real console-script entry point)
- Evidence: `maybe_install_completion` calls `detect_shell()` **before** `ensure_completion()`,
  and `ensure_completion` is the only place that checks `HALIDE_NO_COMPLETION` and
  `sys.stdin.isatty()/sys.stdout.isatty()` (`completion.py:386-391`). `detect_shell()` itself has
  no such guard — it unconditionally does `import psutil; psutil.Process().parent().name()`.
  Measured: `env HALIDE_NO_COMPLETION=1 python -X importtime -m halide.cli.main --help` and the
  same command *without* the env var both import `psutil` (6 matching importtime lines either
  way — no difference). Isolated timing: `import psutil` costs ~29 ms cold in this sandbox,
  against a total `--help` runtime of ~90-110 ms — i.e. ~25-30% of every single non-interactive
  invocation (piped output, CI, scripts, `HALIDE_NO_COMPLETION=1`) is spent on a shell-detection
  probe whose result is then thrown away because `ensure_completion` immediately returns `None`
  for a non-tty session. This contradicts CLAUDE.md's own description: "`HALIDE_NO_COMPLETION=1`
  disables it all, and failures are swallowed" and "When: on every run where stdin/stdout are
  ttys" (implying non-ttys pay nothing). It does not affect batch throughput (runs once per `halide`
  invocation, not per worker) but affects every quick command (`--help`, `check`, `profile list`,
  scripted/tested invocations of the real console script) and every `HALIDE_NO_COMPLETION=1` user.
- Suggestion: move the `interactive`/`HALIDE_NO_COMPLETION` check to the top of
  `maybe_install_completion` (or make `ensure_completion` take an already-known `shell=None` and
  do its own lazy `detect_shell()` call only after the interactive/env-var check passes). Purely a
  startup-time fix; touches no pixel math — bit-identical by construction. Size: S.
- Confidence: confirmed

### 5-6: TIFF write/compression dominates a real batch's CPU time; core color math is a small fraction
- Severity: IDEA (performance characterization, no actionable regression)
- Where: `io/tiff.py` (`compression="zlib", compressionargs={"level": 6}`), `core/density.py`,
  `core/tone_render.py`, `io/icc.py`, `io/lut.py`
- Evidence: `py-spy record --format speedscope` (100 Hz) on a single `invert` of IMG_0158 (single
  process, unambiguous self-time): TIFF `write()` 15.4% self, `apply_density_balance` 8.8%,
  `apply_tone` 4.7%, `Cube1D.lookup` 7.3% (two call sites), ICC `convert_to_working_space` 7.9%
  (three call sites), `read_segments` (decode) 4.5%, module import/bytecode-compile machinery
  (`_compile_bytecode`, `get_data`, `_path_stat`, `add_fns_to_class`) ~15.3% combined — a real, if
  expected, fixed per-process cost that's proportionally large for a single quick `invert`. A
  10-frame, 2-worker `batch` profile (`--subprocesses`, aggregated self-time across all sampled
  threads/processes) showed `compressionfunc`/`decode_other` (tifffile's zlib codec, read+write)
  at a combined ~60% of sampled CPU-seconds, vs. ~17% for halide's own math (density/tone/ICC/LUT).
  A follow-up isolated test (writing the same decoded IMG_0158 frame at zlib levels 6/1/0) found
  **no meaningful win from lowering the level** on this data: 0.35 s / 168.6 MB (level 6) vs.
  0.23 s / 168.7 MB (level 1) vs. 0.27 s / 189.6 MB (level 0, i.e. store) — level 1 is ~34% faster
  in this isolated test with byte-identical compression ratio to level 6, but this doesn't fully
  explain the ~60% aggregate seen in the real batch (likely inflated by summing self-time across
  tifffile's internal compression thread pool across multiple worker processes rather than true
  wall-clock share). Not confident enough in the isolated-test extrapolation to recommend a level
  change without a real before/after batch timing on the user's own machine.
- Suggestion: if pursued, benchmark `compressionargs={"level": 1}` end-to-end on a full Roll16
  batch (wall time + output byte-for-byte decode check, since zlib level only changes the
  compressed bytes, never the decoded pixels — decoding is lossless, so this is bit-identical for
  pixels, not for the TIFF's raw bytes on disk). Size: S to test, M to land (needs the
  decode-equivalence test CLAUDE.md's own bit-identical bar would demand).
- Confidence: likely (the level-6-vs-1 isolated write test is confirmed; the claim that it would
  measurably speed up a real batch is not)

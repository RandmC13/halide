# Task 4: CLI experience walkthrough

Persona: a film photographer who has never seen halide, reading only README.md, on Linux, with
`--device cpu`. Yardstick: R-011..R-014 (professional, verbose-right, consistent, no missing help)
and R-016 (its own darkroom visual identity, never generic). All commands run against a temp
HOME/XDG_CONFIG_HOME under `.review/scratch/4/home`; synthetic 32x32 linear-TIFF-with-ICC fixtures
built the same way `tests/integration/test_invert_cli.py` does (see `.review/scratch/4/make_roll.py`,
`make_mistakes.py`); three real Roll16-Testing frames were used only for the Ctrl-C-mid-batch and
scan-consistency checks and deleted immediately after. No large files or tmux sessions were left
running (verified at the end of this task).

## What works

- **The bare `halide` invocation** (`console.py::welcome_screen`) is genuinely well designed: a
  sprocket-hole (`▫`) rule scaled to the real terminal width, a centered "h a l i d e" wordmark, and
  two curated example workflows ("New here?" / "Editing yourself?") instead of argparse's bare
  "the following arguments are required" error. This is exactly the bespoke, non-generic identity
  R-016 asks for, and it's the single best first impression in the tool.
- **The run sheet** (`console.RunSheet`, `Roll`/`Scans`/`Calibration`/`Output`/`Compute`/`Workers`)
  reads as one coherent, professional block: aligned label column, hanging-indent wrapping that
  respects the real terminal width (checked at 60/80/120/200 columns), sprocket rules that scale
  with `$COLUMNS`. A real scan-consistency warning ("digitized at 2 different camera exposures, 0.3
  stops apart...(--match-scan-exposure corrects this)") surfaced correctly and legibly at all four
  widths.
- **The animated batch grid** (`batch/progress.py`) is a genuine, restrained darkroom animation —
  a static contact-sheet-style strip of frames that pulse while developing and fade to a developed
  tone, plus a live ETA ("~0.9s remaining") — not a generic spinner or progress bar. It matches
  CLAUDE.md's documented intent and doesn't feel bloated at any of the four widths tested.
- **Ctrl-C is clean everywhere tested**: the interactive calibration-source prompt, a mid-frame
  `invert` on a real scan, and a mid-batch cancellation on 3 real Roll16-Testing frames all exited
  130, printed an immediate, accurate status line, left no partial/half-written output TIFF and no
  orphaned worker process (verified with `ps aux` and `ls` on the output dir after each).
- **The ICC/colour validation errors are excellent** when the input's own profile is honest about
  itself: a profile whose TRC tag is genuinely a 2.2 gamma curve is rejected with "this profile is
  gamma-encoded (e.g. for display use). Re-export using your raw processor's linear gamma/tone-curve
  option" — plain language, names the cause, says exactly what to do. `no embedded ICC profile
  found; cannot verify color space` (no-ICC / CMYK inputs) is equally direct. The profile-name-typo
  error is a good example too: `no such profile file 'X', and no saved profile named 'X' found in
  <config dir>` — precise, no jargon.
- **Non-ASCII paths and paths with spaces both just work** end to end (`négatif café/photo été.tiff`
  → `/tmp/positif été.tiff`, and a destination with literal spaces) — no mojibake, no quoting bugs.
- **The overwrite prompt exists and defaults safely** for single-file commands in a real terminal
  (`console.confirm_overwrite`): `path already exists — overwrite? [y/N]`, default No.

## Findings

### 4-1: Every successful `batch`/`export`/`print` run prints the wrong completion message
- Severity: S3 UX friction (borderline S2 — actively misleads about what was produced)
- Where: `src/halide/batch/progress.py:258-261` (`GridProgressRenderer.finish`)
- Evidence: `finish()`'s success branch is hardcoded:
  ```
  print(f"\n{Style.GREEN}{Style.BOLD}Contact sheet complete{Style.RESET} — "
        f"{self.total}/{self.total} frames {verb_past} in {human_time(elapsed)}.")
  ```
  `GridProgressRenderer` is constructed identically (no context flag) from all four call sites —
  `batch_cmd.py:329` (`verb="invert"`), `print_cmd.py:142` (`verb="print"`),
  `export_cmd.py:134` (`verb="export"`), `contact_cmd.py:108` (`verb="proof"`) — so only the
  `contact`/`--contact-sheet` case is actually a contact sheet. Reproduced live:
  `halide batch roll/ out/ --auto-density --workers 1` → `Contact sheet complete — 4/4 frames
  developed in 1.2s.`; `halide export out/ exp/` → `Contact sheet complete — 4/4 frames exported
  in 1.0s.` No `--contact-sheet` flag was passed in either run. A user who ran plain `batch` or
  `export` would reasonably go looking for a "sheet" file that was never created.
- Requirement: R-013 (consistent output), R-011 (professional)
- Suggestion: pass the actual noun (or a `Style`-level "what got made" string) into
  `GridProgressRenderer`/`finish()` instead of a hardcoded label. S (one string, four call sites).
- Confidence: confirmed

### 4-2: The same `finish()` also mis-states successes when there are failures
- Severity: S4 inconsistency / confusing wording
- Where: `src/halide/batch/progress.py:224-233` (`report`), `:252-256` (`finish`, failures branch)
- Evidence: `report()` increments `self.completed` for every result, success or failure
  (`self.completed += 1` unconditionally at line 233). `finish()`'s failure branch then prints
  `f"— {self.completed}/{self.total} frames {verb_past} in ...:"`. Reproduced with a 3-frame batch
  where one input was a non-TIFF text file:
  `Completed with 1 failure(s) — 3/3 frames developed in 1.1s:` followed by the one failure listed
  below it — i.e. it claims all 3 frames were "developed" in the same breath as reporting 1 of them
  failed. It should read something like "2/3 frames developed, 1 failed".
- Requirement: R-013
- Suggestion: track successes and attempts separately; S.
- Confidence: confirmed

### 4-3: `invert IN IN` (output path equal to input) silently destroys the source scan when not run in a real terminal
- Severity: S1 data loss
- Where: `src/halide/cli/console.py:543-549` (`confirm_overwrite`)
- Evidence: `confirm_overwrite`'s own docstring: "Non-interactively, always proceeds (today's
  silent-overwrite behavior, matching batch) rather than blocking a script on input it'll never
  get." Reproduced: `halide invert good.tiff good.tiff --auto-density --device cpu < /dev/null`
  exits 0 and overwrites `good.tiff` in place with the developed positive — the original negative
  scan is gone, with no warning printed at all. In a real pty the same command does prompt
  (`good.tiff already exists — overwrite? [y/N]`, default No) — so this is specifically a
  non-interactive/scripted/cron hazard, not a universal one, but batch scripting is a completely
  normal way to run halide (see `docs/README.md`'s own batch examples), and a typo'd or
  copy-pasted output path is an easy real mistake with no undo.
- Requirement: R-011 ("reliable"), implicit data-safety expectation
- Suggestion: for the single-file commands, non-interactively *refuse* rather than silently
  proceed when input path == output path specifically (this one case is unambiguously never
  intended), even though "no tty, proceed" is fine for a merely-pre-existing different file. S/M.
- Confidence: confirmed

### 4-4: `batch` never prompts or warns before overwriting existing outputs, even in a real terminal

### 4-5: stdout is fully block-buffered when not a tty, so a redirected run can show the error *before* the context that explains it
- Severity: S3 friction, real-world relevant (any `> log.txt 2>&1`, cron, CI)
- Where: no explicit flush/line-buffering anywhere in `cli/console.py`'s `RunSheet`/`print()` calls
  (only two `sys.stdout.flush()` calls exist in the whole file, both inside the spinner/animation
  code — `console.py:409,417`); `console.py:613` writes the top-level exception message to
  `sys.stderr` (which is unbuffered) while `RunSheet` rows go to `sys.stdout` (line- or block-
  buffered depending on tty detection)
- Evidence: `halide batch roll/ out/ --workers 1 < /dev/null > log.txt 2>&1` (no calibration
  source given) produced, in file order:
  ```
  ✗ Error: density balance requires a calibration source: ...
  ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫ ▫
    Roll           roll · 4 frames → /tmp/rollout
    Scans          not checked — no camera EXIF...
  ```
  i.e. the error appears to happen *before* halide even reports what roll/output it resolved. The
  identical command run with `python -u` (unbuffered) produces the rows in the correct logical
  order (Roll/Scans rows, then the error). This is a standard Python stdout-vs-stderr buffering
  artifact when stdout isn't a tty, confirmed by toggling `-u`, not a logic bug in the ordering
  code itself — but it means every redirected/logged halide run (a very normal way to run an
  unattended batch) can show a reordered, confusing story.
- Requirement: R-013
- Suggestion: `sys.stdout.reconfigure(line_buffering=True)` near the top of `cli/main.py`, or flush
  after each `RunSheet` row/print. S.
- Confidence: confirmed (reproduced with/without `-u`)

### 4-6: The batch/export/print/contact progress animation has no non-interactive fallback — only `--quiet` (all-or-nothing)
- Severity: S4 inconsistency, S3 friction for logged runs
- Where: `src/halide/batch/progress.py` (`GridProgressRenderer` — no `isatty` check anywhere in
  the file, confirmed by grep); contrast with `cli/commands/gpu_cmd.py:124` and
  `profile_cmd.py:171`, which do check `sys.stdin.isatty()` before prompting
- Evidence: redirecting a plain 4-frame `batch` run to a file (no `--quiet`) produced 78 lines full
  of raw cursor-up/clear-line ANSI codes (`\x1b[5A\x1b[K...`) for a *4-frame* roll — one full
  5-line redraw per state transition per frame. A real 37-frame roll would multiply this
  proportionally into hundreds of escape-code-laden lines in a log file, unreadable without a
  terminal emulator. There is no middle ground between "full animated redraw" and "nothing" for a
  user who wants a plain progress log (e.g. `batch ... | tee run.log` from cron).
- Requirement: R-012 (verbose in the right ways, not spam), R-013
- Suggestion: when `not sys.stdout.isatty()`, print periodic plain lines ("3/37 developed...")
  instead of the redraw sequence, the way `gpu_cmd.py`/`profile_cmd.py` already gate their own
  interactivity on `isatty()`. M.
- Confidence: confirmed

### 4-7: halide's own colours ignore `NO_COLOR` and non-tty output; only the stdlib-argparse portion of the same output respects it
- Severity: S4 inconsistency
- Where: `src/halide/cli/console.py:31-39` (`class Style` — hardcoded ANSI escapes, no
  `NO_COLOR`/`isatty` check anywhere in the class or its callers, confirmed by grep for `isatty`/
  `NO_COLOR` in the file: the only 4 `isatty()` calls are for prompts, none for output styling)
- Evidence: `NO_COLOR=1 halide --help` still emits 2 pairs of raw `\x1b[2m...\x1b[0m` codes around
  the `help_banner()` rule/tagline, while the argparse-generated usage/options text below it
  correctly loses all colour (Python 3.13+'s stdlib argparse has its own `NO_COLOR`-aware
  colourizer). Likewise `halide invert missing.tif out.tif 2>&1 | cat -v` (piped, non-tty, with
  ambient `FORCE_COLOR` explicitly unset) still shows `^[[91m✗ Error:^[[0m` literally in the
  output — halide's `error()`/`warning()`/`success()`/`RunSheet` never check `NO_COLOR` or
  `isatty()` before emitting escape codes. Any redirect-to-file, `less` without `-R`, or `grep`
  over halide's own output gets escape-code noise that the tool's *own* argparse-half doesn't
  produce.
- Requirement: R-013
- Suggestion: gate `Style`'s codes on `sys.stdout.isatty() and not os.environ.get("NO_COLOR")`
  (matching Python's own `can_colorize` logic, importable from `_colorize` on 3.13+, or a small
  local equivalent). M.
- Confidence: confirmed

### 4-16: Bad-format/wrong-shape inputs crash through the generic exception boundary with raw library errors instead of a plain-language message
- Severity: S2 bug (crashes with a message a photographer cannot act on)
- Where: `src/halide/cli/console.py:610-614` (catch-all `except Exception` boundary); no dedicated
  validation for channel count in `io/tiff.py`/`io/icc.py` before `convert_to_working_space`'s
  matmul
- Evidence (all reproduced, exit 1 in every case, all via the same "halide hit an unexpected
  error: ..." wrapper with only "(re-run with --debug...)" as a next step):
  - An RGBA TIFF (valid RGB-tagged linear ICC, 4-channel pixel data — a real, plausible mistake if
    a "keep alpha" export box is left checked): `matmul: Input operand 1 has a mismatch in its core
    dimension 0, ... (size 3 is different from 4)`.
  - A single-channel greyscale TIFF (RGB-tagged ICC, 1-channel data): `matmul: ... (size 3 is
    different from 32)` — note "32" is the image's pixel *width*, not a channel count; the message
    is actively misleading even to a technical reader.
  - A JPEG passed as input: `not a TIFF file: header=b'\xff\xd8\xff\xe0'`.
  - A fake `.CR3` (garbage bytes): `not a TIFF file: header=b'\x00\x01FA'`.
  - A fake `.NEF`: two raw, unfiltered `tifffile` library lines print directly to the terminal
    before the wrapped error —
    `<tifffile.TiffPages @1162559814> invalid offset to first page 1162559814` (twice), then
    `halide hit an unexpected error: index 0 out of range(0)`.
  In every one of these, the well-designed ICC-specific checks (`no embedded ICC profile found`,
  `not a linear tone curve`, `color space is ...`) simply never get a chance to run, because the
  failure happens earlier (file-format sniffing) or later (the channel-count matmul) than where
  those checks live.
- Requirement: R-013, "is the error in plain photographer's language, and does it say what to do
  next?" (task 4.3's own yardstick) — none of these five do.
- Suggestion: (a) validate channel count (==3, RGB) right after ICC validation, before any matmul,
  with a message like "expected 3 channels (RGB), found 4 — strip the alpha channel before
  exporting" / "found 1 (greyscale) — halide needs a colour scan"; (b) catch `tifffile`'s
  not-a-TIFF error at the same layer and say "this doesn't look like a TIFF (halide doesn't read
  RAW/JPEG directly — export a linear TIFF from your raw developer first)"; (c) suppress or
  redirect `tifffile`'s own stderr chatter. M.
- Confidence: confirmed

### 4-20 (nuance, not a bug): a gamma-encoded file whose ICC profile *itself* claims to be linear cannot be caught
- Severity: none — documented as an IDEA/limitation, not a defect
- Where: `src/halide/io/icc.py::parse_linear_rgb_profile`
- Evidence: built a TIFF with a genuinely linear-tagged ICC profile (`rTRC`/`gTRC`/`bTRC` =
  identity curves) but manually gamma-encoded (`**(1/2.2)`) pixel data — halide accepted and
  processed it without complaint (it has no way to know the pixel data doesn't match its own
  tag). Verified this is *not* a gap in halide's real-world claim: built the honest case (a
  profile whose TRC tag genuinely declares gamma 2.2, matching `tests/unit/test_icc.py`'s own
  `test_rejects_gamma_encoded_trc`) and it was correctly rejected with an excellent message (see
  "What works"). README's claim ("gamma-encoded ... halide rejects it") holds for every realistic
  case (a raw developer exporting display-gamma output tags it as such); the only way to defeat it
  is a mistagged/hand-edited file, which is inherent to how ICC profiles work, not fixable without

- Confidence: confirmed (both the mistagged case and the honest case were built and run)

## IDEA (missing features — no argument for building, per brief)

- **Dry run** (`--dry-run` / `--what-if`): no such flag exists anywhere (grepped all `add_argument`
  calls). A Negative Lab Pro / Grain2Pixel user moving from a GUI where you always see a live
  preview before committing might want a way to see "would process N frames with profile X, output
  print @ ~exposure Y" without writing files, especially for a big roll.
- **Overwrite control** (`--overwrite`/`--no-clobber`/`--skip-existing`): see 4-3/4-4 above — no
  explicit flag exists; behaviour today is an unconfigurable prompt-or-silent split by command and
  tty-ness. darktable/Lightroom-adjacent tools generally offer an explicit choice.
- **Output naming control** (a filename template, not just `--suffix`): `--suffix` exists on
  batch/export/print, but there's no way to change the naming scheme itself (e.g. `{stem}_dev`,
  numbered sequences, or writing into subfolders by roll/date) — a Grain2Pixel/NLP user is used to
  Lightroom's naming templates.
- **Recursive folder input**: confirmed non-recursive (`orchestrator.py:163`'s `iterdir()`); a
  roll organized into subfolders (e.g. by contact-sheet "picks") is invisible today, silently (see
  4-18).
- **A log file** (`--log FILE`): today the only record of what happened is the terminal output
  itself (or a redirected copy, which per 4-5/4-6 is noisy without `-u`/non-interactive handling);
  no structured per-run log alongside the output folder.
- **A man page or `--examples`**: see 4-9 — no per-command worked examples in `--help` at all
  today; a man page is a bigger ask most CLI tools in this space (rawtherapee-cli, darktable-cli)
  also skip, but `--examples` is cheap and other tools in this space (e.g. `restic`, `rclone`) do
  it well.
- **An end-of-batch summary with more than a count**: today's summary is one line (count + time,
  modulo the 4-1/4-2 wording bugs) — no breakdown by output size, no per-frame grade/exposure
  recap (even though that data exists — the contact sheet captions it per-frame already, per
  CLAUDE.md), which an NLP/Grain2Pixel user reviewing a whole roll's consistency might want without
  opening every file.
- **Shell completion, ETA, ✓/✗ per-item status**: already present and good (`halide`'s own
  completion self-install, the batch grid's `~Xs remaining`, per-frame pulse/fade) — noted here
  only so they aren't mistakenly proposed again later.

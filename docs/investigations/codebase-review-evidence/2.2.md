### 2.2-1: Profile names are never validated, so `../`, absolute-looking names, and OS limits reach the filesystem raw
- Severity: S1 accuracy/data-loss
- Where: `src/halide/calibration/profile_store.py:101-213` (`save_named_profile`, `rename_profile`,
  `update_profile`, `delete_profile` all do `directory / f"{name}.json"` with zero sanitization);
  `cli/commands/profile_cmd.py` passes `args.name`/`args.old_name`/`args.new_name` straight through.
- Evidence: ran (script `.review/scratch/2.2/test_delete_traversal.py`):
  ```
  sentinel = <profiles_dir>.parent / "sentinel-important.json"   # OUTSIDE the profiles dir
  delete_profile("../sentinel-important")
  sentinel exists after: False
  ```
  `halide profile delete ../anything` (or `rename`/`--save-profile-as`) deletes/overwrites a file
  one level above the profiles directory — not sandboxed to it. Also (`test_names.py`):
  `save_named_profile(p, "../evil2")` succeeds and writes to
  `<profiles_dir>/../evil2.json` (i.e. outside the profiles dir), and a 300-character name raises a
  raw `OSError: [Errno 36] File name too long` that isn't caught anywhere — reproduced live through
  the real CLI: `halide invert IMG_0151.tif out.tif --rm 1 --bm 1 --save-profile-as <300 a's>` prints
  `✗ Error: halide hit an unexpected error: [Errno 36] File name too long: '...'`.
- Requirement: none explicit, but violates the general "photographer-friendly errors" bar and the
  brief's own callout (profile names with `/`, `..`, very long).
- Suggestion: validate/sanitize the name once in `profile_store.py` (reject `/`, `..`, empty, and
  anything over a sane length with a clear `ValueError`) before it ever reaches a `Path`. S.
- Confidence: confirmed.

### 2.2-2: `--save-profile-as`/re-saving under an existing name silently overwrites it — no warning, no confirmation
- Severity: S1 accuracy/data-loss
- Where: `src/halide/calibration/profile_store.py:101-117` (`save_named_profile` never checks
  `path.exists()` before writing).
- Evidence (`.review/scratch/2.2/test_overwrite.py`):
  ```
  save_named_profile(p1, "Roll16")   # notes="original calibration - important"
  save_named_profile(p2, "Roll16")   # notes="oops overwrite"
  load_profile(...) -> notes='oops overwrite'   # p1 is gone, no error, no prompt
  ```
  Unlike `rename_profile`, which does raise `FileExistsError` for a rename onto an existing name,
  the far more common path (`--save-profile-as NAME` on `invert`/`batch`) has no such guard.
  CLAUDE.md is explicit that profiles are "meant to be solved once per film-stock/process/scanner
  combination and reused" — i.e. exactly the kind of file a typo'd re-run (or a second person's
  `--save-profile-as` on the same shared roll) can destroy silently.
- Requirement: none explicit; matches the brief's "rename onto an existing name" ask but the more
  dangerous gap is on *save*, not rename.
- Suggestion: `save_named_profile` should warn/prompt (or refuse) exactly like `rename_profile`
  does, reusing `console.confirm`. S.
- Confidence: confirmed.

### 2.2-5: Profile writes aren't atomic; a truncated/corrupt profile then crashes `--profile NAME` with a raw JSON parser message
- Severity: S2 bug
- Where: `src/halide/calibration/profile_store.py:61` (`save_profile`: plain
  `Path(path).write_text(...)`, no temp-file+`os.replace`), same pattern in `rename_profile:177`
  and `update_profile:204`. `cli/_calibration_args.py:250-260` (`resolve_density_profile`) only
  catches `FileNotFoundError` around `load_profile`, not `json.JSONDecodeError`/`ValueError`.
- Evidence (`.review/scratch/2.2/test_corrupt.py`, simulating a crash mid-write by truncating the
  file to half its bytes — the same end state a crash between `open()` and `write()` leaves):
  ```
  list_profiles() -> Warning: skipping unreadable profile .../corruptme.json: Unterminated string...
  load_profile(resolve_profile_path("corruptme")) -> JSONDecodeError: Unterminated string...
  ```
  Live through the CLI: `halide profile show corruptme` prints
  `✗ Error: halide hit an unexpected error: Unterminated string starting at: line 13 column 3 (char 131)`
  — no filename, no hint that a saved profile is the thing that's broken, and no suggestion to
  delete/recalibrate. (A missing-field profile, by contrast, already gets a decent message —
  `load_profile`'s own `ValueError` includes the path and field name — this finding is specifically
  about the un-caught `JSONDecodeError` case.)
- Requirement: brief's "corrupt or hand-edited JSON," "atomic writes."
- Suggestion: write via a temp file + `os.replace` for atomicity (S), and catch
  `(json.JSONDecodeError, ValueError)` around every `load_profile`/`load_*` call reached from a CLI
  command, turning it into a `SystemExit` that names the profile file and suggests
  `halide profile delete`/recalibrating (S).
- Confidence: confirmed.

### 2.2-6: A single NaN (or non-positive) pixel silently produces a NaN density-balance profile in `--auto-density`/`--auto-density-roll`
- Severity: S1 accuracy/data-loss
- Where: `src/halide/calibration/auto.py:132-143` (`_saturation`). The "not positive" branch
  (`not_positive = ~(max_channel > 0)`, which the docstring says "includes NaN") sets that pixel's
  *saturation to 0* — i.e. treats a NaN/zero/negative pixel as the single most-neutral candidate
  possible — instead of excluding it from candidacy. `_check_density_separation` (line 153-156)
  computes `span < MIN_DENSITY_SEPARATION` with NaN operands, which is always `False`, so its own
  safety-net warning never fires either.
- Evidence (`.review/scratch/2.2/test_auto_degenerate.py`):
  ```
  img = np.full((20,20,3), 0.3, dtype=np.float32); img[0,0,:] = np.nan
  auto_density_balance(img)
  -> DensityProfile(white_balance=(nan, nan, nan), density_scale=(nan, nan, nan), ..., source='auto')
  ```
  No exception, no warning (only a `RuntimeWarning: invalid value encountered in divide`, which
  reads as noise, not a diagnosis). Feeding this into `develop()`/`process_scan` would silently
  turn an entire frame into NaN — a total failure with no error message naming the cause. This is
  a real risk surface, not purely synthetic: CLAUDE.md already documents that this exact pipeline
  produces extreme/out-of-range values that need a floor clamp elsewhere (`MIN_TRANSMITTANCE`,
  `core/invert.py`) — `auto.py` runs on the *pre-invert* transmittance image and applies no such
  floor before ranking pixels by saturation.
- Requirement: brief's "behaviour on degenerate frames," and the project's top priority
  (colorimetric faithfulness / never silently wrong).
- Suggestion: exclude non-finite/non-positive pixels from candidacy entirely (mask them out, not
  saturation-zero them in), and raise a clear `ValueError` if the profile solve produces any
  non-finite value. S/M.
- Confidence: confirmed.

### 2.2-8: A profile named with a leading "-" can be saved but can't be referenced by `profile show/rename/delete/edit` without the undocumented `--` separator

### 2.2-9: `halide check` treats "no EXIF found in any frame" the same as "nothing wrong," and accepts a non-TIFF file passed directly as an input
- Severity: S3 UX friction
- Where: `cli/commands/check_cmd.py:23-32` (`_collect`: filters by suffix only when scanning a
  *directory*; a file named directly is appended unconditionally) and
  `calibration/scan_consistency.py:80-138` (`RollScanReport.has_issues`/`summary_lines` never
  reference `missing_exif` at all — it's computed but only ever read by `check_cmd.py` itself).
- Evidence:
  ```
  $ halide check <folder-of-2-tiffs-with-no-EXIF-at-all>
  Checked 2 scan(s)
    Camera exposure when digitizing
             (no EXIF)    2 frame(s)  plain1.tif, plain2.tif
  # no ⚠, no "consistent" ✓ either — plain uncolored text
  $ echo $?
  0
  ```
  and
  ```
  $ echo "not a tiff" > notes.txt
  $ halide check notes.txt

    Camera exposure when digitizing

  ```
  A roll whose exporter/scanner strips EXIF entirely — or a stray non-TIFF file passed by mistake

  on Roll16-Testing, `shadhi` active on `IMG_0158.tif`, white-balance spread on the four scans) —
  so the tool works correctly when EXIF exists; this finding is specifically about the "nothing to
  check" case reading as "checked, fine."
- Requirement: brief's "missing or odd EXIF... how `halide check` presents results."
- Suggestion: when `missing_exif` covers the whole input, print an explicit note ("no camera EXIF
  in any frame — exposure consistency can't be checked") rather than leaving a bare, uncolored
  count; and have `_collect` validate suffix/readability even for explicitly-named files. S.
- Confidence: confirmed.

### 2.2-12: No macOS-native config path, and no protection against case-insensitive-filesystem name collisions
- Severity: S4 inconsistency
- Where: `calibration/profile_store.py:21-24` (`default_profiles_dir`: always
  `$XDG_CONFIG_HOME/halide/profiles` or `~/.config/halide/profiles`, on every platform).
- Evidence: code inspection only — no macOS available in this sandbox. `~/.config` does work on
  macOS (readable/writable, and plenty of cross-platform CLIs use it), so this isn't broken, but
  (a) it's not where a macOS user would look (`~/Library/Application Support/halide` is the
  platform convention), and (b) combined with 2.2-2's unconditional overwrite: on APFS/HFS+'s
  default case-insensitive-but-preserving mode, `save_named_profile(p, "Portra")` followed later by
  `save_named_profile(p, "portra")` would resolve to the *same* file (the OS treats them equal),
  silently overwriting the first under its original filename with the second's content — with the
  same "no warning" gap as 2.2-2, just reachable through a case typo instead of an exact-name typo.
- Requirement: brief's "macOS: 'Portra' vs 'portra'"; brief's "$XDG_CONFIG_HOME and macOS paths."
- Suggestion: not urgent (the directory works); if 2.2-2 is fixed with an overwrite prompt, this
  case falls out for free. Document the actual on-disk location for macOS users in the README. S.
- Confidence: likely (reasoned from code + the confirmed general-overwrite behavior; the
  case-insensitivity mechanism itself is standard, well-documented macOS filesystem behavior, not
  something that needed independent verification here).

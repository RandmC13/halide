### 7.1-1: `batch`/`export`/`print`'s success message always says "Contact sheet complete", even for ordinary runs that made no contact sheet

- Severity: S3 UX friction
- Where: `src/halide/batch/progress.py:258-261` (`GridProgressRenderer.finish()`); verb table at
  `src/halide/cli/console.py:60-61`
- Evidence: ran `halide batch .review/scratch/7.1/minirol .review/scratch/7.1/minirol-out
  --auto-density --device cpu --workers 1` (no `--contact-sheet`) — two full TIFFs were correctly
  written, but the final line printed was:
  `Contact sheet complete — 2/2 frames developed in 18.0s.`
  Same on `halide export ... --format jpg` (`Contact sheet complete — 2/2 frames exported in
  4.7s.`). Only the real `halide contact` run's message is actually correct for that wording. Code:
  ```python
  else:
      print(
          f"\n{Style.GREEN}{Style.BOLD}Contact sheet complete{Style.RESET} — "
          f"{self.total}/{self.total} frames {verb_past} in {human_time(elapsed)}."
      )
  ```
  — the success branch hardcodes "Contact sheet complete" instead of using `verb`/`verb_past`
  the way the string right above it already does for the failure branch.
- Requirement: R-013 (CLI output aesthetically consistent), R-011 (feels designed)
- Suggestion: use a verb-specific noun (e.g. a small `{"batch": "Batch", "export": "Export",
  "print": "Print", "proof": "Contact sheet"}` map) in that f-string. S.
- Confidence: confirmed (reproduced on real scans for batch and export; read for print/invert,
  which share the same renderer/verb table)
- Cross-reference: independently found and already filed in more detail as **2.3-6**; listed here
  because it's exactly the kind of "description vs. actual behaviour" mismatch this task's README
  walkthrough was asked to catch, and because README's Commands table implies each command's own
  vocabulary ("Developed", "Exported") rather than this.

### 7.1-4: `roll_auto_density_balance`'s docstring describes the *old*, since-replaced per-frame reference ("its own per-channel median"), not the density-local one it actually calls

- Severity: S4 inconsistency (misleading to a future maintainer)
- Where: `src/halide/calibration/auto.py:242`: "Selects neutral candidates *per frame first* (each
  judged against its own per-channel median), then pools only the resulting candidate pixels..."
- Evidence: the function this describes, `_neutral_candidates` → `_neutral_candidate_mask`, calls
  `_density_local_saturation` (`auto.py:64`), whose own docstring says it judges each pixel "against
  the per-channel median of *other pixels at a similar density*... replacing a single frame-wide
  median." CLAUDE.md's own "Decisions and why" (the `_saturation`/density-local-reference entry)
  documents this replacement as a real, structural bug fix — a single per-channel median was shown
  to misclassify neutrals (the traffic-light/hair/sign example). `roll_auto_density_balance`'s
  docstring was written (or left) describing the pre-fix behaviour it no longer has; only the
  *pooling-order* part of that docstring (its actual subject — per-frame selection before roll-wide
  pooling) is still accurate.
- Requirement: R-009 (density-local fix is a settled decision — this doesn't reopen it, just flags
  the docstring drift)
- Suggestion: drop "(each judged against its own per-channel median)" or replace with "(each judged
  density-locally, see `_density_local_saturation`)". XS.
- Confidence: confirmed

### 7.1-5: `core/pipeline.py`'s module docstring ("Both the CLI and the GUI call this — neither reimplements the math independently") is no longer true of the CLI's full-resolution path

- Severity: S5 polish (precision, not a behaviour bug — the reimplementation is deliberate and
  verified bit-identical elsewhere)
- Where: `src/halide/core/pipeline.py:1-2`
- Evidence: `grep -rn "run_pipeline\|core\.pipeline import" src/halide/` shows `run_pipeline` is
  imported nowhere in `src/` outside `pipeline.py` itself — only from `tests/unit/test_pipeline.py`
  and `tests/integration/test_icc_pipeline_integration.py`. `processing.py:24` imports only
  `negative_to_positive` from `core.pipeline`, and `_develop_in_place` (`processing.py:395-404`)
  calls `negative_to_positive`/`resolve_tone`/`apply_tone` directly, banded, rather than
  `develop()`/`run_pipeline()` — exactly as `_develop_in_place`'s own (accurate, and honest about
  it) docstring says: "the same per-pixel stages in the same order... Bit-identical to develop()".
  Only `gui/render.py:19` actually imports and calls `develop`/`negative_to_positive` from
  `pipeline.py`. So today it's the GUI, not the CLI's full-resolution path, that literally "calls
  this"; the CLI calls the same underlying stage functions banded, not `run_pipeline`/`develop`
  themselves. The banding refactor (CLAUDE.md, "Every full-resolution path now works band by band")
  predates and explains this but the module docstring wasn't updated to say so.
- Requirement: R-008 (one composed pipeline entry point / no duplicated chains) — worth flagging
  precisely because this is the kind of claim R-008 is supposed to guarantee
- Suggestion: reword to something like "core/pipeline.py: the whole-array reference chain. The GUI
  calls it directly; the CLI's full-resolution path (processing.py::_develop_in_place) runs the
  same stage functions banded and is pinned bit-identical to it in test_banding.py." S.
- Confidence: confirmed

## IDEA: where CLAUDE.md's length could move to docs/, by heading

Not a defect — CLAUDE.md's own content is accurate (see above); this is purely about readability.
Everything under **"Decisions and why"** is a mix of a one-line decision (belongs in CLAUDE.md) plus
paragraphs of supporting measurement (candidate for `docs/`). By heading, the ones with the most
evidence-per-decision, roughly in order of how much they'd shrink the file:

- **GPU acceleration** (the largest block by far: CuPy rationale, namespace-generic core, fake
  device, D1/D2 tolerance decisions, per-worker constants, the user's probe numbers, the
  2026-09-27 verification table) — most of this already has a home in `docs/plans/
  gpu-acceleration.md` and `docs/plans/gpu-acceleration-bench.py`; CLAUDE.md could shrink to the
  one-paragraph decision ("optional, CuPy, `--device auto` default, D1/D2 tolerance") plus a link.
- **A GPU service process shared by CPU-only workers** (the whole B0-B5 measurement narrative,
  `/dev/shm` failure-mode list, worker-count formulas) — already has a home in
  `docs/plans/gpu-batch-throughput.md` and `docs/investigations/gpu-batch-throughput.md`.
- **`batch.orchestrator.default_worker_count` sizes the worker pool from available RAM** and its
  two sub-bullets (the ~4x RSS multiplier investigation, the banding rewrite's per-command RSS
  table) — this narrative isn't currently backed by a docs/ write-up at all; it would need a new
  `docs/investigations/memory-budgeting.md` rather than moving to an existing one.
- **`--auto-density-roll` / density-local `_saturation`** two entries (the traffic-light/hair/sign
  investigation, the rejected "consensus" idea) — already has a home in spirit; nothing under
  `docs/investigations/` currently covers it specifically, so this would also be a new file.
- **Manual calibration fits any number of user-picked neutral points** and **the picker's design**
  — already summarized versions of `docs/investigations/anchor-frame.md` and
  `docs/plans/multipoint-picker.md`; CLAUDE.md's copies could shrink to a decision line + link.
- Kept in CLAUDE.md as-is: "What this project is", "Decisions and why" *headlines* only, "Working
  with the user" — these are short and are exactly what a newcomer skimming the guide needs.

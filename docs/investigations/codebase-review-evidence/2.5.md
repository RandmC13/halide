Scope covered: `src/halide/cli/main.py`, `console.py`, `completion.py`, `_calibration_args.py`,
`_device_args.py`, `_run_sheet.py`, `_contact_sheet.py`, all of `src/halide/cli/commands/*.py`, and
`src/halide/batch/progress.py`. All findings below were checked against the running CLI
(`.venv/bin/python -m halide.cli.main ...`) unless marked `likely`. Real scans (`IMG_0156.tif`) were
used for reproductions that needed a real TIFF; all scratch outputs were deleted immediately after

## String inventory observations

(Full inventory: `.review/strings.tsv`, ~155 rows.)

- **"Error:"/"Warning:" text prefix vs. bare icon for success.** `error()` and `warning()` both
  print an icon *and* a capitalized word ("✗ Error:", "⚠ Warning:"), but `success()` prints only
  the icon with no "Success:"/"Done:" word (`console.py:111-120`). Reads as intentional (success
  doesn't need announcing) but is worth confirming it's deliberate rather than a gap.
- **Two different "clear this field" conventions for the same command.** `profile edit`'s flag
  form documents "pass '' to clear" (`profile_cmd.py:58-61`) while its interactive-prompt form
  documents "type a single '-' to clear it" (`profile_cmd.py:147`) — same subcommand, same fields,
  two different literal tokens with no cross-reference in either help text.
- **`--workers` help text depth varies command to command** for the identical flag/behaviour:
  `batch_cmd.py:72-77` gives a full paragraph (RAM vs. CPU reasoning), `print_cmd.py:57-59` and
  `export_cmd.py:56-58` give a shorter restatement, and `contact_cmd.py:38` gives one terse clause
  ("default: auto-selected") with no reasoning at all.
- **Stated defaults are inconsistent within one flag group.** `--rs`/`--bs` say "(default: 1.0)"
  in their help; the functionally parallel `--rm`/`--bm` (also effectively 1.0 when omitted, per
  `resolve_density_profile`) state no default at all (`_calibration_args.py:47-54`).
- **Vocabulary**: "frame" is used almost everywhere for one image in a roll; `profile show`'s
  scan-settings line says "Scanned at:" while other places say "digitized at" or "scan exposure" —
  minor, but the ledger/CLAUDE.md itself is careful about frame/scan/negative/positive/print
  wording elsewhere, so this file is a slight outlier.
- **Punctuation**: most sentences in longer help/warning text end without a full stop; a few
  (`"Not installed."`, `"No changes made."`, `gpu_cmd.py`'s status lines) end with one. Not wrong,
  just not uniform — a pass over `strings.tsv` would need to pick one convention.
- **A hardcoded, wrong heading**: see 2.5-3 below — `GridProgressRenderer.finish()`'s success
  message says "Contact sheet complete" unconditionally, even for `invert`/`batch`/`export`/`print`
  runs that never touched a contact sheet. This is the single clearest wording bug found.
- Full completeness caveat: the inventory covers every string literal in the CLI-owned files above.
  Strings raised from `core/`, `io/`, `calibration/`, `processing.py` etc. and only *passed through*
  a CLI `except: raise SystemExit(str(exc))` are included only where a command actually surfaced
  one during testing (e.g. the ICC/TIFF errors below) — a full pass over those modules' own message
  text is Task 2.1/2.2/2.3's job, not re-duplicated here.

### 2.5-1: `batch`/`print`/`export` bulk modes never check for an existing output file, and no command checks output-path == input-path — a source scan can be silently destroyed
- Severity: S1 accuracy/data-loss
- Where: `src/halide/cli/commands/batch_cmd.py` (`run`/`_run`, no `confirm_overwrite` call anywhere in
  the file); `src/halide/batch/orchestrator.py:159-169` (`discover_jobs`, no existence check);
  `src/halide/cli/commands/print_cmd.py::_run_bulk`; `src/halide/cli/commands/export_cmd.py::_run_bulk`
  (same absence). Contrast with `invert_cmd.py:149`, `print_cmd.py:82`, `export_cmd.py:74`, which do
  call `console.confirm_overwrite` for their *single-file* mode.
- Evidence (all reproduced, outputs deleted immediately after):
  1. `halide invert /tmp/test_same.tif /tmp/test_same.tif --auto-density` (output = input) silently
     overwrote the source file (125,443,238 bytes → 137,184,272 bytes, no prompt, no warning), even
     though `confirm_overwrite` exists in this exact code path — it only ever checks "does the file
     exist", not "is it the same file as my own input".
  2. `halide batch /tmp/halide_batch_same /tmp/halide_batch_same --auto-density --quiet` (output_dir
     == input_dir) silently overwrote the only copy of the source scan in place
     (md5 `28b29b36...` → `83f64f92...`), exit code 0, no warning printed anywhere on the run sheet.
  3. Re-running `halide batch` into an *already-populated* (but different) output folder silently
     replaced the existing output file with no prompt and no diagnostic, even though this is exactly
     the scenario `console.confirm_overwrite` exists to guard against for the single-file commands.
- Requirement: matches Review Focus item 2 verbatim ("Re-running into a folder that already has
  outputs, or output = input. Expect no silent overwrite of a user's scan.") — this expectation is
  violated for every multi-file command in the CLI.
- Suggestion: (a) in every bulk `run()`, resolve and compare `input_path.resolve()` against each
  computed output path and refuse (or warn strongly) on a collision; (b) route each `BatchJob`
  destination through `confirm_overwrite`-style logic before file `write` happens (or at least warn
  once on the run sheet "N of M outputs already exist and will be overwritten" so an interactive
  user gets a chance to Ctrl-C). This is used in production by a photographer with irreplaceable
  scans — worth prioritizing over most other findings in this file. M-size fix.
- Confidence: confirmed

### 2.5-4: NO_COLOR and TERM=dumb are not honoured anywhere — ANSI escapes always print, even to a pipe
- Severity: S3 UX friction
- Where: `src/halide/cli/console.py` (`Style` class and every helper built on it — `success`,
  `error`, `warning`, `rule`, `RunSheet`, `animation`, etc. — none check `NO_COLOR`/`TERM`); the only
  tty-awareness anywhere in `console.py` is `animation._active = sys.stdout.isatty()` (line 381),
  which stops the *redraw* but not the color codes on the label line itself.
- Evidence:
  ```
  $ NO_COLOR=1 .venv/bin/python -m halide.cli.main --help | cat -v
  ^[[2m▫ ▫ ▫ ...^[[0m
    ^[[1mhalide^[[0m · develop scanned color negative film
  $ TERM=dumb .venv/bin/python -m halide.cli.main --help | cat -v
  (identical — raw escape codes present)
  ```
  Reproduced identically whether piped, with `NO_COLOR=1`, or with `TERM=dumb`; no code path
  suppresses `Style.*` codes under any of these conditions. `grep -rn "NO_COLOR\|TERM\b" src/` finds
  nothing, and `grep -rn NO_COLOR tests/` finds no test either.
- Requirement: this is one of the review brief's explicit checklist items for Task 2.5
  ("NO_COLOR / TERM=dumb support in console.py").
- Suggestion: gate `Style.*` constants (or wrap every emitted code) behind
  `sys.stdout.isatty() and not os.environ.get("NO_COLOR") and os.environ.get("TERM") != "dumb"`,
  computed once at import or lazily per call. M-size (touches every color constant, but
  mechanically — a single `_color_enabled()` gate reused everywhere would do it).
- Confidence: confirmed

### 2.5-5: A failed shell-rc edit is stamped as "done" and never retried, even after the underlying problem is fixed
- Severity: S3 UX friction (tab completion silently and permanently never installs)
- Where: `src/halide/cli/completion.py:397-428` (`ensure_completion`) — `setup.stamp.touch()` (line
  413) runs *before* the `try: ... setup.rc.open("a", ...)` block that can fail (lines 418-426); the
  next run's `first_time = not setup.stamp.exists()` (line 397) is then permanently `False`.
- Evidence (reproduced with `ensure_completion` called directly, bypassing the swallowing wrapper to
  observe the real state):
  ```
  # run 1, .zshrc chmod 400 (read-only)
  RAISED: PermissionError(13, 'Permission denied')
  stamp exists: True
  # .zshrc chmod 600 (now writable)
  # run 2
  note: None
  zshrc contents: ''   # never written, ever again
  ```
  In the real CLI path (`maybe_install_completion`), the `PermissionError` is swallowed silently (by
  design, per the module's own docstring — "every failure is swallowed"), so the user never even
  sees the failure that caused this. The module's docstring claims "A stamp file per shell makes
  that a one-time step: a user who deletes the block ... doesn't get it back" — but the same
  mechanism also permanently discards a *transient* failure (a momentarily read-only $HOME during
  disk pressure, a home-manager/chezmoi apply running concurrently, a full disk), which was not the
  intended case.
- Requirement: relates to Task 2.5's completion.py checklist item ("safety — idempotent? handles a
  read-only ... .zshrc?"). Idempotency is fine when the write succeeds; this is the failure path.
- Suggestion: only touch the stamp file after the rc write actually succeeds (move
  `setup.stamp.touch()` to after the `with setup.rc.open("a", ...)` block, or wrap the whole
  first-time sequence so a raised exception skips the stamp). S-size fix.
- Confidence: confirmed

### 2.5-6: Writing a shell's completion script file replaces a symlink with a plain file (breaks chezmoi/home-manager-managed dotfiles)
- Severity: S4 inconsistency (silent, narrow — only affects users who symlink-manage their fish
  completions directory) / IDEA to harden
- Where: `src/halide/cli/completion.py:369-378` (`_write_if_changed`, uses `tmp.replace(path)`);
  applies most concretely to `shell_setup("fish").target` =
  `~/.config/fish/completions/halide.fish` (`completion.py:350`), the one completion target that
  lives directly in a conventional dotfiles-managed directory (zsh/bash targets live under
  `~/.local/share/halide/completion/`, halide's own private directory, so this is much less likely
  to bite there).
- Evidence: confirmed the underlying mechanism directly (not the full chezmoi/home-manager scenario,
  which needs those tools installed):
  ```
  $ ln -sf realfile.txt link.txt
  $ python3 -c "from pathlib import Path; p=Path('link.txt'); t=p.with_name(p.name+'.tmp'); \
                t.write_text('NEW'); t.replace(p)"
  $ ls -la link.txt   # now a plain regular file, not a symlink
  $ cat realfile.txt  # unchanged — the symlink's original target was never touched
  ```
  `Path.replace()` unlinks the destination and puts the new file in its place; if the destination
  was a symlink into a dotfile manager's store, the manager's tracked symlink is silently destroyed
  and replaced by an untracked plain file (which the manager would likely then either overwrite back
  on its next apply — silently discarding halide's freshly generated completions — or flag as a
  manual/local modification, depending on the tool).
- Requirement: Task 2.5 checklist item ("a .zshrc managed by home-manager/chezmoi?" — same question,
  applied to the fish completion file rather than the rc file itself; the *rc* files are opened with
  `.open("a")`, which correctly follows a symlink rather than replacing it, so this is specific to
  the completion-script write path).
- Suggestion: if `setup.target` is a symlink, either write through it (open for write instead of
  replace) or skip managing it and print a hint — S-size.
- Confidence: confirmed (mechanism); "affects real home-manager/chezmoi users" is `likely`, not
  independently reproduced with those tools.

### 2.5-8: stdout is buffered, stderr is not — the fatal error line appears *before* the output that led to it in any redirected/logged run
- Severity: S3 UX friction (misleading log order for exactly the non-interactive use case scripts rely on)
- Where: `src/halide/cli/console.py:613` (fatal error → `print(..., file=sys.stderr)`) vs. every
  other command print (`print(console.warning(...))`, progress/animation labels, `print(...)`) which
  go to stdout, unbuffered-vs-buffered by Python's default stream policy (stderr unbuffered, stdout
  block-buffered when not a tty).
- Evidence (reproduced with a plain redirect, not a pipe, to rule out a `tail`/pager artifact):
  ```
  $ halide invert /tmp/fake.tif /tmp/out.tif --auto-density > /tmp/out.log 2>&1
  $ cat /tmp/out.log
  ✗ Error: halide hit an unexpected error: not a TIFF file: header=b'not '
  (re-run with --debug, or set HALIDE_DEBUG=1, for the full traceback)
  ⚠ Warning: GPU not usable, using CPU instead: ...
  Developing fake.tif...
  ```
  Chronologically, "Developing fake.tif..." and the GPU warning print *first* in the real run — the
  log shows them last. Anyone debugging a failed unattended batch job from a captured log (the
  primary reason people redirect CLI output at all) sees the conclusion before the cause.
- Requirement: general "is the message useful" / robustness checklist item; not explicitly named in
  the brief but squarely a CLI-output-design defect per Task 4.2's "Output design audit" concerns.
- Suggestion: flush stdout before any stderr write in `run_guarded` (`sys.stdout.flush()` right
  before the `print(..., file=sys.stderr)` calls), or make stdout line-buffered for this CLI
  regardless of tty status. S-size.
- Confidence: confirmed

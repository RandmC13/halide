### 2.6-1: Saving a profile with a bad name (or any disk error) fails completely silently in the GUI
- Severity: S1 accuracy/data-loss
- Where: `src/halide/gui/main_window.py:292-304` (`SaveProfileDialog._on_save_clicked`)
- Evidence: `_on_save_clicked` calls `save_named_profile(self._profile, name, **self._sidecars)`
  (line 302) with no try/except. `profile_store.save_profile` (`src/halide/calibration/profile_store.py:61`)
  does a bare `Path(path).write_text(...)`. Reproduced directly: typing `sub/name` into the Save
  dialog's name field (no validation rejects `/`) and clicking Save raises
  `FileNotFoundError: [Errno 2] No such file or directory: '.../profiles/sub/name.json'`
  (`.review/scratch/2.6/test_save_dialog_stays_open.py`). The exception propagates out of the Qt
  slot, is printed to stderr by the interpreter's default excepthook, and **the dialog does
  nothing else**: it stays open, `dlg._message.text()` is still `"Name this calibration:"`
  (never updated), and `dlg.result()` stays `0` (never accepted). A user who launched `halide
  calibrate` from a desktop icon (no visible terminal) sees the Save button appear to do nothing —
  no error dialog, no status text — and has no way to know the save failed. The exact same
  unguarded call path fires for a full disk or a permissions error on `~/.config/halide/profiles/`.
- Requirement: R-104 (the one red Save button is the GUI's entire persistence step)
- Suggestion: wrap the `save_named_profile` call in `try/except (OSError, ValueError)` and show
  the error in `self._message` (or a `QMessageBox`) instead of letting it escape; validate the
  name against `os.sep`/`os.altsep` up front with a clear message ("profile names can't contain
  a slash") rather than only ever discovering it from a stack trace. S (small, targeted fix).
- Confidence: confirmed

### 2.6-2: Rebuilding the contact sheet silently breaks its own staleness tracking after the first rebuild
- Severity: S2 bug
- Where: `src/halide/gui/main_window.py:873-899` (`_on_proof`, `_on_proof_closed`, `_proof_is_stale`)
- Evidence: `_on_proof` does, in order: `self._proof.close()` (877-878, if a window is already
  open), builds a brand-new `ProofWindow` and assigns it to `self._proof` (887-890), then connects
  `self._proof.destroyed.connect(self._on_proof_closed)` (891). `ProofWindow` has
  `WA_DeleteOnClose` (proof_window.py:237), so `.close()` schedules a **deferred** `deleteLater()`;
  the old window's `destroyed` signal (connected to `_on_proof_closed` the *first* time it was
  built) doesn't fire until the event loop next turns — i.e. strictly *after* `_on_proof` has
  already reassigned `self._proof` to the new window. When it does fire, `_on_proof_closed` sets
  `self._proof = None`, clobbering the reference to the live, currently-shown new window.
  Reproduced the exact Qt timing mechanism in isolation (`.review/scratch/2.6/test_proof_stale_ref.py`):
  building a second "proof" while the first is still around leaves the holder's reference `None`
  even though the second widget is alive and `isVisible() == True`. This is not a rare double-click
  race — it is the code path `mark_stale`'s own "Rebuild contact sheet" button uses
  (`self._proof.mark_stale(self._on_proof)`, line 899, wires the button straight to `_on_proof`).
  So: build a contact sheet, change a point (marks it stale, offers "Rebuild"), click "Rebuild
  contact sheet" — after that, `self._proof` is `None` even though the rebuilt window is open on
  screen. Change another point: `_proof_is_stale` (897-899) checks `if self._proof is not None`
  and silently no-ops. The user now has a contact sheet that no longer reflects their calibration,
  with no stale marker and no offer to rebuild — exactly the failure mode contact sheets exist to
  catch (CLAUDE.md: "the check that the neutral points picked on a few frames hold up across every
  frame of the roll").
- Requirement: R-107, R-108
- Suggestion: don't rely on the `destroyed` signal to null out `self._proof`; capture the specific
  window instance in the closure (`lambda w=new_window: self._on_proof_closed(w)` and compare
  identity), or track proof windows by id, or simply reset `self._proof = None` *before* calling
  `.close()` on the old one on line 878, since the old window's own destroyed-driven callback should
  never touch the new window's slot. S/M.
- Confidence: confirmed (Qt signal-timing mechanism reproduced in isolation; not exercised through
  a fully loaded MainWindow+roll+profile session end to end — Phase 6 should verify the "pick,
  build, edit, rebuild, edit again" sequence visually against this prediction).

### 2.6-3: Rebuilding (or replacing) the contact sheet blocks the main window's UI thread
- Severity: S3 UX friction
- Where: `src/halide/gui/proof_window.py:370-375` (`ProofWindow.closeEvent`), called synchronously
  from `main_window.py:878` (`self._proof.close()`)
- Evidence: `closeEvent` calls `self._renderer.requestInterruption()` then
  `self._renderer.wait()` with **no timeout** ("No timeout: Qt aborts the whole process if a
  running QThread is destroyed", per the code's own comment). `_on_proof` calls `.close()`
  directly on the GUI/main thread, so the whole window (filmstrip, points, everything) is
  unresponsive for however long the in-flight `ProofRenderer` takes to notice
  `isInterruptionRequested()` (its loop polls every 0.2s, `proof_window.py:129`) and its worker
  processes to actually exit (`_wait_for_exit(processes)`, awaited unconditionally when the loop
  was still pending). On a real roll this is bounded but non-trivial — the CLAUDE.md-recorded
  worker teardown/GPU-service-stop sequence isn't instant.
- Requirement: R-108
- Suggestion: at minimum, disable/grey the "Build/Rebuild contact sheet" affordance and show a
  "closing previous sheet…" status while `.close()` runs, or make the close asynchronous (start
  the new window only after the old one's `destroyed` fires). M.
- Confidence: likely (read only — the blocking call is unambiguous in the code; wall-clock impact
  not measured here since it needs a real roll + workers).

### 2.6-4: No cap on concurrent full-resolution frame loads when scrubbing the filmstrip
- Severity: S3 UX friction
- Where: `src/halide/gui/main_window.py:673-691` (`_select_frame`), `src/halide/gui/loaders.py:65-83`
  (`FrameLoader`)
- Evidence: every call to `_select_frame` unconditionally disconnects the *signal* of any
  in-flight `FrameLoader` (line 688) and starts a brand-new one (689-691) — it never asks the old
  one to stop, and `FrameLoader.run()` has no `isInterruptionRequested()` check at all, so it
  can't be stopped anyway (this is by design — full-res decode "can't be interrupted mid-decode",
  per the `_stop_loaders` docstring at line 730). Each of these is a full
  `load_working_space_image` call: decode + ICC-to-ACEScg conversion of a full-resolution scan,
  which CLAUDE.md's own worker-sizing investigation measured at ~150-500 MiB peak RSS and real
  wall-clock time per frame (the exact same call `default_worker_count`/`estimate_worker_memory_bytes`
  exist to budget for in `batch/orchestrator.py`). Nothing here budgets it: a user clicking
  through several filmstrip frames in quick succession (a very ordinary way to browse a roll)
  starts that many concurrent full-resolution decodes, all but the last of which are discarded by
  the guard in `_on_frame_loaded` (line 699: `if ... .path != path: return`) once they finish —
  wasted CPU/memory pressure that stacks the same way the `--auto-density-roll` OOM CLAUDE.md
  documents did, just via a different trigger (rapid clicks, not many workers).
- Requirement: none directly (no R-nnn covers picker responsiveness/memory), but this is the same
  class of problem R-005/the worker-sizing decisions in CLAUDE.md were written to prevent
  elsewhere.
- Suggestion: ignore/cancel-and-restart cheaply (a monotonically increasing "request token" the
  callback checks) so at most the most-recently-requested load's *decode* actually gets kicked off
  after a short debounce, or accept the outstanding one runs to completion but don't start the next
  until it's done. S/M.
- Confidence: likely (read only; the absence of any guard or debounce is unambiguous, but the
  actual memory/latency impact needs a real large-frame roll to measure — Roll16-Testing under
  Phase 6 would show this as filmstrip-click lag on a memory-constrained machine).

### 2.6-5: `--save-profile-as` silently overwrites an existing profile; the GUI explicitly guards this
- Severity: S1 accuracy/data-loss
- Where: `src/halide/cli/_calibration_args.py:295-321` (`maybe_save_profile`) vs.
  `src/halide/gui/main_window.py:292-301` (`SaveProfileDialog._on_save_clicked`)
- Evidence: the CLI's save path calls `save_named_profile(profile, save_as, tone=tone, scan=scan)`
  (line 321) unconditionally — no existence check anywhere in `maybe_save_profile` or in
  `profile_store.save_named_profile`/`save_profile`. Running e.g. `halide invert a.tif b.tif
  --auto-density --save-profile-as Portra400` a second time (different points, different
  negative) overwrites a real, previously-solved `Portra400.json` — the exact profile CLAUDE.md
  says is meant to be "solved once per film-stock/process/scanner combination and reused" — with
  zero warning, exit code 0. The GUI's `SaveProfileDialog._on_save_clicked` (lines 297-301)
  explicitly checks `(default_profiles_dir() / f"{name}.json").exists()` first and requires a
  second, deliberate click (button relabelled "Overwrite") before proceeding. This is a real
  behavioural asymmetry between the two front ends to the same operation, and the CLI side is a
  standing silent-overwrite risk on its own regardless of the GUI. (This overlaps Task 2.2's/2.5's
  scope — profile_store.py / cli/_calibration_args.py — flagging it here since Task 2.6 explicitly
  asks to compare the two save flows.)
- Requirement: R-040/R-042 area (profiles "solved once... and reused")
- Suggestion: give the CLI the same guard: refuse (or require `--force`) when
  `<name>.json` already exists unless explicitly confirmed, matching the GUI's behaviour. S.
- Confidence: confirmed (read directly; both code paths quoted above)

### 2.6-7: No HiDPI (devicePixelRatio) awareness anywhere in the GUI's custom painting
- Severity: S4 inconsistency
- Where: `src/halide/gui/main_window.py:107-113` (`_qimage`), `:79` (`_DISPLAY_BUDGET = (1600, 1100)`),
  and generally across `gui/`
- Evidence: `grep -rn "devicePixelRatio\|PixelRatio" src/halide/gui/` returns nothing. `_qimage`
  builds a `QImage` from the numpy array with no `setDevicePixelRatio` call, so it defaults to
  1.0; `positive_display`/`negative_display` always render into the fixed
  `_DISPLAY_BUDGET = (1600, 1100)` logical-pixel budget (`downsample_for_display`,
  `sampling.py:46-61`) regardless of the *physical* pixel density of the screen the window ends up
  on. `_compute_window_size` sizes the window from `screen.availableGeometry()`, which Qt reports
  in device-independent (logical) points, so on a 2x HiDPI display the image area can need up to
  ~2x as many *physical* pixels as `_DISPLAY_BUDGET` provides, and `SmoothPixmapTransform`
  (main_window.py:172) will upscale/smooth over that gap rather than the display genuinely
  resolving detail at native density. This doesn't affect accuracy — picks are always sampled from
  the full-resolution buffer regardless of what's on screen (`sampling.py`'s docstring, and
  `_on_image_clicked` maps back through `stride`, never through the display pixmap) — but it means
  the picker's own preview, which is what a user judges "is this really neutral" from at a glance
  before zooming with the magnifier, is softer on a HiDPI machine than the panel it's shown on
  could support.
- Requirement: none specific; relevant to Phase 6's planned `QT_SCALE_FACTOR=2` pass
- Suggestion: scale `_DISPLAY_BUDGET` (and the magnifier's zoom canvas) by
  `QGuiApplication.primaryScreen().devicePixelRatio()`, and set it on the `QImage`/`QPixmap` via
  `setDevicePixelRatio()` so Qt doesn't re-stretch an already-correct-resolution image. S/M.
- Confidence: likely (code-absence confirmed directly; visual softness not measured — Phase 6's
  `QT_SCALE_FACTOR=2` screenshots should show this concretely, or disprove it if Qt's own pixmap
  scaling compensates more than this reading credits)

### 2.6-8: A frame that fails to load has no visible reason until you click into it
- Severity: S5 polish
- Where: `src/halide/gui/filmstrip.py:98-99` (`_Strip.paintEvent`), `main_window.py:658-671`
  (`_on_preview_ready`)
- Evidence: on a preview load error, `_on_preview_ready` only calls
  `self.filmstrip.strip.set_pixmap(index, None, failed=True)` (line 664) — the string in
  `frame.error` (set on the line above) is stored but never shown anywhere for a *non-current*
  frame. `_Strip.paintEvent` paints a failed frame as a plain dark-red-brown fill
  (`"#3a1a18"`, see 2.6-6) with no `setToolTip` call anywhere in the class. The only way to learn
  *why* a specific frame failed (corrupt TIFF, unsupported ICC profile, etc.) is to click it,
  which starts a `FrameLoader` for it and — only then — surfaces the real message via
  `_on_frame_loaded`'s `self._status(f"Error: {error}")` (line 703). For a roll where one frame
  out of many is bad, a user has to guess-and-click to find out which one and why.
- Suggestion: `_Strip.set_pixmap`/`set_frames` could carry the error string and set it as that
  frame cell's tooltip. S.
- Confidence: confirmed (code read; behaviour matches directly)

## Things checked and found fine (worth recording so they aren't re-checked)

- **Stale-loader signals for the *preview* pool are handled correctly.** `_stop_loaders` (line
  728) disconnects `previewReady` before a new `PreviewLoader` is created for a new roll/profile,
  so a slow-finishing preview from the *previous* roll can never call into `_on_preview_ready`
  with indices/paths belonging to the new one. Confirmed by reading `_start_roll` (which always
  calls `_stop_loaders()` before building the new loader) and `PreviewLoader.run`'s per-future
  `previewReady.emit`.
- **Frame-loader disconnect-then-replace is race-free for the *current* frame.** `_select_frame`
  disconnects the old `FrameLoader.loaded` signal before wiring the new one; `_on_frame_loaded`
  additionally guards on `self.session.frames[self._current].path != path`. The only issue is the
  *resource* one in 2.6-4, not a correctness/stale-data one.
- **Backspace/Delete do not fight with text-field editing.** The window-level
  `QShortcut(Qt.Key.Key_Backspace/Key_Delete, ...)` (main_window.py:352-353) could plausibly
  conflict with editing the "Extra information" / Save-dialog text fields. Verified directly with
  a minimal repro (`.review/scratch/2.6/test_shortcut_conflict.py`, `QTest.keyClick` into a
  focused `QLineEdit`): the text field consumes Backspace itself; the window shortcut does **not**
  fire while a `QLineEdit` has focus. Ruled out — not a finding.
- **Empty/degenerate rolls are handled without destroying existing session state.**
  `load_roll` (line 534) computes the TIFF-filtered file list *before* asking to discard the
  current calibration or resetting anything; a folder with zero TIFFs just prints
  `"No TIFF scans in {folder}"` and returns, leaving whatever was loaded before untouched.
- **Non-TIFF files in a roll folder are filtered silently, but this matches every CLI command.**
  `load_roll`'s `p.suffix.lower() in TIFF_SUFFIXES` filter (line 535) is the same silent-filter
  pattern `batch/orchestrator.py`, `check_cmd.py`, `export_cmd.py` and `print_cmd.py` all use — a
  tool-wide convention, not a GUI-specific inconsistency. (Could still be a mild IDEA tool-wide —
  "N non-TIFF files ignored" — but out of scope for a GUI-only finding.)
- **Portrait frames and tiny/huge images**: `ImageView._image_rect` fits both axes independently
  (`scale = min(avail_w/pix.width(), avail_h/pix.height())`), so portrait content pillarboxes
  correctly; `downsample_for_display` and `extract_magnifier_patch` both handle degenerate/small
  inputs (radius-clamped slicing, edge-padding) without special-casing — read through, no crash
  path found.
- **Temp-folder/process cleanup for the proof renderer** is solid: `ProofRenderer.run`'s
  `shutil.rmtree(folder, ignore_errors=True)` is in a `finally` around the whole body, so it runs
  on interruption or exception; `_develop`'s own `finally` terminates outstanding worker processes
  and waits for them to actually exit before the caller's temp-folder cleanup runs.
- **Profile-open error handling.** `open_profile` catches `(ValueError, KeyError, OSError)` around
  `session.restore`, covering a profile deleted between file-dialog selection and open, a
  corrupted/hand-edited JSON, and a profile missing required fields.

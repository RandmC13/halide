## Reference check (not findings: the pipeline is correct)

I checked it step by step against `abpy/color-neg-resources` (`density levels.py`, `neglut.py`,
`density balance.js`) and `alchemy-color/color-negative-inversion` (its `density balance.js` has the
same maths as abpy's).

- **White balance, then density balance, then invert, in linear ACEScg:** same order and same maths.
  abpy does `rgb*mult`, then `max(.0001, ch)`, then `log10(1/ch)*scale`, then `10**ch * .01`.
  halide does `img*wb`, then `max(img, 1e-7)`, then `x**s`, then `1/x`. `x**s` is the same as the
  scaled density, just without the log round trip.
- **`solve_density_balance`:** I ran abpy's `density levels.py` unmodified. It prints
  wb = (2.277304130526006, 1, 1.4658041418862766) and scale = (1.318585760497101, 1, 0.7777660280302214),
  which are exactly the numbers pinned in `tests/unit/test_density.py`. `fit_density_balance` with two
  points agrees to about 1e-15. The model is D_c = log10(wb_c) + D_G/s_c. I derived it by hand, and
  `neutral_residuals` and `leave_one_out_residuals` both follow from it. A synthetic check (5 points
  on a known line, one pushed +0.05 D in red) gives a leave-one-out row of (+0.0433, −0.0217, −0.0217),
  which is exactly s_r·0.05 minus its mean.
- **Paper curve:** the data in `assets/tone_curves/paper_endura.cube` is byte-identical to abpy's
  `paper_a.cube` (checked with `cmp`). Normalising by the maximum matches `neglut.py`. The curve input
  is log10(positive), which equals the balanced negative density, and that matches
  `ch += base_exposure; curve[ch/3]`.
- **The fit_print algebra:** I checked it by hand. With the fitted grade, D_hi maps to the highlight
  point and D_lo to the shadow point. Multiplying the input by any constant changes only the exposure.
- **Colour management does not add a cast:** on the real scans' embedded profiles (v2.4 curv
  "Linear Rec2020 RGB", and Elle's v4.3 para ACEScg), the rXYZ+gXYZ+bXYZ columns sum to D50 and
  wtpt = D50. RGB (1,1,1) comes out in ACEScg as (0.99990, 1.00006, 0.99974), which is at most
  1.4e-4 D (CC 0.01) off neutral. The ACEScg→sRGB export uses Bradford to D65, so neutrals stay
  neutral there too.

Deliberate differences from the references:

| Difference | Covered by a decision? |
|---|---|
| Working space is ACEScg (abpy). alchemy works in Rec.2020. | Yes ("ACEScg, chosen") |
| Exposure and grade are fitted per frame. abpy uses a fixed `base_exposure=0.43` and has no grade. | Yes ("default tone-render curve", "print fit") |
| Curve lookup interpolates linearly. abpy rounds to the nearest of its 1024 entries. | No. It's harmless and an improvement (smoother tones, the same curve). Worth one line in a docstring. |
| Floor is 1e-7. abpy uses 1e-4. | No. Negligible: real scans' 0.1th percentile is ≥ 0.004 in every channel (IMG_0156, IMG_0158, Roll16/IMG_0138). |
| The flat output is scaled from a percentile. abpy multiplies by a fixed ×0.01. | Yes ("mode=linear is scaled") |
| Neutral points are fitted by least squares across frames. The references take two eyedropper samples. | Yes ("Manual calibration fits any number…") |
| alchemy uses a Levels black/white point after the curve. | Rejected by a decision ("never a post-curve stretch") |
| Output is an ACEScg TIFF. abpy writes a ProPhoto 1.8 3D LUT. | Yes (TIFF-in/TIFF-out architecture) |

### 2.1-1: The Save gate accepts neutral points only 0.1 D apart, and a fit through them can be CC 8-15 off at the ends of the tonal range with nothing warning the user
- Severity: S1 accuracy
- REOPENS: "Manual calibration fits any number of user-picked neutral points" (the 0.1 D
  `MIN_DENSITY_SEPARATION` minimum, used as the gate for Save and for agreement readings). New
  evidence is the simulation below.
- Where: src/halide/calibration/anchors.py:89-95 (`can_fit`), src/halide/calibration/auto.py:61
- Evidence: I simulated true neutrals on a known film line (wb 2.2/1/1.4, s 1.3/1/0.78) with 3
  picked points and a small independent per-channel sampling error. I then scored the fitted
  profile on true neutrals at D_G 0.4 and 1.6 (the ends of a typical negative):
  ```
  3 points spanning 0.1 D, pick noise 0.005 D: worst-end CC median 7.7, 90th pct 14.4
  3 points spanning 0.1 D, pick noise 0.01 D:  worst-end CC median 15.1, 90th pct 31.1
  3 points spanning 0.3 D, pick noise 0.005 D: worst-end CC median 2.9, 90th pct 5.5
  3 points spanning 0.6 D, pick noise 0.005 D: worst-end CC median 1.8, 90th pct 3.3
  ```
  A pick error of 0.005 D (CC 0.5) is far smaller than the CC 1-5 non-neutrality CLAUDE.md measured
  on real "trusted" whites. The agreement readings can't catch this. Points that agree with each
  other, all within one 0.1 D band, still read "calm", and 2-point profiles get no reading at all.
  The error only shows up when the line is extrapolated to shadows and highlights.
- Suggestion: report how uncertain the fit is, not only how far apart the points are. The lstsq
  covariance (or leave-one-out spread) gives a predicted CC error at the ends of the wedge
  (`wedge_range`). Show it in the picker ("fit reliable over D 0.9-1.3 only"). Either raise the
  Save gate to about 0.3-0.5 D or warn below it. M.
- Confidence: confirmed (simulation; not measured on the user's own picks)

### 2.1-2: One NaN or inf pixel ruins the whole frame: a print crashes with an index error, and a flat output is written as all NaN and reported "✓ Developed"
- Severity: S2
- Where: src/halide/core/tone_render.py:132 and :207 (`percentile` over NaN gives NaN),
  src/halide/io/lut.py:314 (`floor_t.astype(int32)` of NaN), src/halide/processing.py:103 (json
  NaN)
- Evidence (60x80 synthetic scans with one bad pixel, `.review/scratch/2.1/mk.py`):
  ```
  halide invert nan.tif … --rm 0.9 --bm 1.1 --rs 1.1 --bs 0.8
  ✗ Error: halide hit an unexpected error: index -2147483648 is out of bounds for axis 0 with size 1024
  halide invert inf.tif …            -> same error (inf becomes NaN in the ICC matmul: inf·(−coef) + inf)
  halide invert nan.tif … --auto-density -> same error
  halide invert nan.tif … --output flat
  flat output: exposure scale ×nan
  ✓ Developed → out/nan_flat.tif        finite fraction 0.0
  desc {"halide": {"output": "flat", …, "linear_scale": NaN, …}}   <- not valid JSON for non-Python readers
  ```
  `estimate_linear_scale`'s `if highlight <= 0` guard is False for NaN, so NaN passes through.
  `fit_print` behaves the same way: `min(NaN, 1.0)` returns NaN. IMG_0158 already has one negative
  pixel, so non-finite values from a raw converter (highlight reconstruction, darktable modules) are
  plausible.
- Suggestion: clean the data once, at the working-space boundary. In `_read_scan` or
  `_to_working_space`, map NaN to 0 and ±inf to 0 or the maximum, per band, and count them. Warn
  ("N pixels were not numbers; treated as clear film") and keep the statistics finite. Or use
  `nanpercentile` and fail with a clear message. Also add `allow_nan=False` to `provenance_json`.
  Is it bit-identical on clean input? Yes, if it only touches non-finite values. S.
- Confidence: confirmed

### 2.1-3: The ICC "is it linear?" check uses an absolute 5e-3 tolerance in linear light, which is far too loose where a negative's values sit (0.004-0.05 in blue)
- Severity: S2
- Where: src/halide/io/icc.py:35 (`_LINEARITY_TOLERANCE = 5e-3`), :144 (11 sample points), :168
  (`np.allclose(..., atol=...)`)
- Evidence (`hostile_icc.py`, `quantify.py`): these are all ACCEPTED as linear:
  ```
  para0 g=1.013 / g=0.987                 ACCEPTED
  para4 f=0.004 (black offset)            ACCEPTED
  curv with 21 entries, zig-zag between the 11 sample points   ACCEPTED
  density error they cause:  T=0.01: gamma1.013 −0.026 D, offset0.004 +0.146 D
                             T=0.03: gamma1.013 −0.020 D, offset0.004 +0.054 D
  ```
  Real-scan blue ranges from 0.0043 (0.1th percentile) to 0.05 (median) on IMG_0158. Density
  balance works in log units, so an absolute error that looks tiny near 1.0 becomes up to CC 15 of
  error, different per channel, in the negative's dense areas. This is exactly what the validator
  exists to reject. The likelihood is low: real RawTherapee/darktable linear profiles are curv
  count 0/1 or para g=1, and all of them pass exactly.
- Suggestion: compare in density. For example, require |log10(response/x)| < 0.002 at log-spaced x
  in [1e-3, 1]. Sample every table entry of a `curv` rather than 11 points, and check it's
  monotonic. S.
- Confidence: confirmed

### 2.1-9: `describe_cast` pairs a CMY dial size with a hue letter, so a two-filter cast reads as the wrong single filter
- Severity: S4
- Where: src/halide/core/density.py:199-210
- Evidence:
  ```
  describe_cast([+0.10, 0, -0.10]) -> (20.0, 'R')
  ```
  Relative to neutral this print is red +0.1 and blue −0.1. On a dichroic head the correction
  pack (subtract the maximum) is **20Y + 10M**, which is roughly CC10R + CC10Y, an orange cast.
  The magnitude max−min equals the largest CMY dial, and that dial always belongs to the complement
  of the *most lacking* channel. The letter, though, is the channel with the largest |deviation|.
  Here that's a tie, and argmax picks R. For (0.1, −0.03, −0.07) the result is "CC 17 R", while the
  pack is 13M+17Y (≈ CC13R + CC4Y). The docstring says CC is "the unit of a dichroic enlarger
  head's filter dials", and a darkroom printer will read "CC 17 R" as one 17R filter.
- Suggestion: either name the letter after the largest dial (the complement of `argmin`, which is
  "CC 20 Y" in the first example), or show the two-filter pack ("CC 20Y 10M"). Pick one convention
  and document it. The agreement bands don't change, because the magnitude stays the same. S.
- Confidence: confirmed

## Checked and fine
- `solve_density_balance`, `fit_density_balance` (2 points), `neutral_residuals`, the
  leave-one-out algebra, the direction of `scan_gain` (reference/frame), and `can_fit`/`agreement`
  gating.
- ICC: s15Fixed16 is signed big-endian `>i`/65536. curv count 0 = identity, count 1 = u8Fixed8
  gamma, n-entry tables are interpolated correctly. para types 0-4 match ICC.1:2010 §10.18
  exactly, and type 5 or higher is rejected. LUT-based tags are rejected. v2 (curv) and v4 (para)
  profiles both parse.
- A uniform frame, a 1x1 frame, zero pixels, and uint16 TIFFs all develop (the grade falls back to
  1.0 when the density span is 0, so there's no division by zero). `estimate_linear_scale` on an
  all-zero input returns 1.0.
- Real prints are barely outside the sRGB gamut (IMG_0156 / IMG_0158 auto: <1% of pixels with any
  channel <0, <0.15% with any >1), so the per-channel clip at export is a minor effect, as
  documented.

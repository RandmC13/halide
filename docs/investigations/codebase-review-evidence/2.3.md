Scope: `src/halide/processing.py`, `banding.py`, `batch/orchestrator.py`, `batch/progress.py`,
`io/tiff.py`, `io/contact_sheet.py`, `cli/commands/{invert,batch,print,export,contact}_cmd.py`.
All reproductions below used synthetic linear TIFFs built with `tests.unit.test_icc.build_icc` +

### 2.3-1: `batch`/`print` into the same directory as the input, with a matching extension, permanently destroys the original scans — no guard exists anywhere
- Severity: S1 accuracy/data-loss
- Where: `src/halide/batch/orchestrator.py:159-169` (`discover_jobs` — builds `output_path = output_dir / name` with no check against `input_path`), used unchanged by `cli/commands/batch_cmd.py:202-208` and equivalently by `cli/commands/print_cmd.py:118-126` (`_run_bulk`, fixed `.tif` output extension regardless of the input's own suffix).
- Evidence:
  ```
  $ md5sum roll/a.tif
  e74661c...
  $ halide batch roll roll --rm 2.28 --bm 1.47 --rs 1.32 --bs 0.78 --workers 1 --quiet
  (exit 0, no warning of any kind)
  $ md5sum roll/a.tif
  7adf390...   # original negative is gone; this is now the *positive*
  ```
  Reproduced identically for `halide print` (a flat `a.tif` printed into its own directory with no
  `--suffix`): the flat positive is overwritten by the printed one, exit 0, no warning.
- Requirement: Review Focus item 2 ("output path == input path... expect no silent overwrite").
- Suggestion: In `discover_jobs` (and print's bulk job list), reject up front (before any
  processing starts) any job whose `output_path.resolve() == input_path.resolve()` — a `SystemExit`
  naming the colliding file(s) and suggesting `--suffix`. This is the one case that must be a hard
  error, not merely a confirm-to-overwrite: it isn't "overwriting an existing file," it's "using a
  scan as both the input and the output of the same run." S (a handful of lines + a test).
- Confidence: confirmed.

### 2.3-2: No bulk command checks for pre-existing output files at all — `batch`/`print --bulk`/`export --bulk` silently overwrite prior outputs (or unrelated stray files with the same name), unlike every single-file command
- Severity: S1 accuracy/data-loss
- Where: `cli/commands/batch_cmd.py` `run()`/`_run` (no `console.confirm_overwrite` anywhere in the
  file); `cli/commands/print_cmd.py:118-183` `_run_bulk`; `cli/commands/export_cmd.py:106-175`
  `_run_bulk`. Contrast with every single-file path, which does check: `invert_cmd.py:148-150`,
  `print_cmd.py:81-83`, `export_cmd.py:73-75`, and `contact_cmd.py:76-77` for the sheet itself.
- Evidence:
  ```
  $ echo SENTINEL > out/f1.tiff        # a stray file, not a halide output
  $ halide batch roll out --rm 2.28 --bm 1.47 --rs 1.32 --bs 0.78 --workers 1
  ... no mention of f1.tiff anywhere on the run sheet or in the output ...
  $ cat out/f1.tiff
  <binary TIFF data — the sentinel is gone>
  ```
  Ran both with and without `--quiet`; neither prints anything about the pre-existing file.
- Requirement: Review Focus item 2.
- Suggestion: Before starting the pool, scan `[job.output_path for job in jobs if job.output_path]`
  for pre-existing files and either refuse (like the single-file commands, non-interactively) or at
  minimum report a single run-sheet line ("N of M outputs already exist and will be overwritten")
  so a re-run into the same folder isn't silent. Given batch is normally non-interactive anyway
  (confirm_overwrite always proceeds without a tty), a single aggregate warning is probably the
  right level rather than per-file prompts. M (touches three command modules + the run sheet).
- Confidence: confirmed.

### 2.3-3: `write_tiff` has no atomic write — a failure partway through (disk full, kill -9, power loss) leaves a truncated file at the exact final output path, indistinguishable by name from a complete one
- Severity: S1 accuracy/data-loss
- Where: `src/halide/io/tiff.py:118-129` (`write_tiff` calls `tifffile.imwrite(path, ...)` directly — no temp file + rename).
- Evidence: mounted a 200 KiB tmpfs (`unshare -m -r`, unprivileged) and called `write_tiff` directly
  with a ~1 MiB random-noise frame:
  ```
  write_tiff RAISED: OSError [Errno 28] No space left on device
  $ ls -la tinyfs2/
  -rw-r--r-- 1 root root 204800 out.tiff        # exactly the tmpfs capacity — truncated mid-write
  ```
  The exception propagates correctly (this isn't silently swallowed), but the half-written file is
  left at `out.tiff` — the same path every caller (`process_scan`, `print_scan`,
  `export_delivery_image`, all three worker functions in `orchestrator.py`) treats as "the output."
  A batch worker's `except Exception` in `_worker`/`_print_worker`/`_export_worker` reports this
  frame as failed (good), but does not delete the truncated file it leaves behind, so a later
  `os.path.exists(output_path)` (e.g. a naive re-run script checking what's already done) sees a
  file there.
- Requirement: Review Focus item 3 ("no half-written TIFF that looks complete").
- Suggestion: Write to `path.with_suffix(path.suffix + ".tmp")` (or `tempfile.NamedTemporaryFile`
  in the same directory, for same-filesystem atomicity) and `os.replace()` onto the real path only
  after `imwrite` returns successfully; on any exception, unlink the temp file. Same treatment for
  `set_description`'s `tifffile.tiffcomment` (rewrites the file in place) and for
  `copy_exif_metadata`'s `-overwrite_original`, though exiftool already does its own temp-file
  dance internally (see 2.3-4) so that one is lower priority. M — one shared helper, used from
  `write_tiff` and ideally by the batch worker to clean up on the exception path too.
- Confidence: confirmed.

### 2.3-4: A post-write exiftool failure (e.g. disk full) surfaces as an uncaught "unexpected error" even though `write_tiff` already wrote a fully valid, complete output file
- Severity: S2 bug
- Where: `src/halide/processing.py:242-257` (`process_scan`: `write_tiff` completes inside the
  `with contextlib.ExitStack()` block; `copy_exif_metadata` and `set_description` run *after* it,
  unguarded) and `io/tiff.py:157-174` (`copy_exif_metadata` — "a failure exiftool reports for the
  file raises"). Neither `invert_cmd.py:154-167` nor `batch/orchestrator.py:_worker` catches
  anything but `ScanColorError`/broad-`Exception`-as-string, so the raw exception (or its `str()`)
  reaches the user.
- Evidence: same tmpfs technique, sized so `write_tiff`'s ~1.5 KB output fits but exiftool's
  `-overwrite_original` temp copy doesn't:
  ```
  ✗ Error: halide hit an unexpected error: Warning: Bad length ICC_Profile (length 0) - roll/f1.tiff
  Error: Error writing output file - tinyfs/out.tiff
      0 image files updated
      1 files weren't updated due to errors
  exit=1
  ```
  But the file at `out.tiff` is in fact a complete, valid, correctly-colour-managed TIFF —
  confirmed by reading it back with `halide.io.tiff.read_tiff` (shape and ICC profile both
  correct). The command reports total failure for a frame that actually developed correctly; only
  its EXIF copy and provenance description (`set_description`, which never even runs — it's after
  `copy_exif_metadata` in `process_scan`) are missing. In a batch, this frame is counted as an
  `error` in `BatchResult`, inflating the failure count and exit code for a frame whose pixels are
  fine.
- Suggestion: Catch exiftool failures separately from decode/calibration failures and report them
  as a *warning* on an otherwise-successful frame ("developed, but couldn't copy EXIF metadata:
  ...") rather than a hard error — the pixel result is what colorimetric faithfulness cares about;
  metadata is explicitly documented elsewhere as "a nice-to-have, not a correctness requirement."
  M (needs a distinct exception type from `copy_exif_metadata`, already half-true via
  `ExifToolError`/`CalledProcessError` — just needs to be caught and demoted at the `process_scan`/
  `print_scan` call sites).
- Confidence: confirmed.

### 2.3-5: Filesystem/library errors reach the user as raw technical text, and the whole frame is processed before an unwritable output directory is even discovered
- Severity: S3 UX friction
- Where: `cli/commands/invert_cmd.py` (no pre-flight check that `output_path.parent` is writable
  before `process_scan` runs the full pipeline inside the themed animation);
  `batch/orchestrator.py:_worker`'s `except Exception as exc: return BatchResult(..., error=str(exc))`
  passes the raw exception text straight through.
- Evidence:
  ```
  $ chmod 555 outdir
  $ halide invert f1.tiff outdir/out.tiff --rm ... 
  Developing f1.tiff...                                    # full pipeline already ran
  ✗ Error: halide hit an unexpected error: [Errno 13] Permission denied: '.../outdir/out.tiff'
  (re-run with --debug, or set HALIDE_DEBUG=1, for the full traceback)

  $ halide batch roll outdir --rm ... --workers 1 --quiet   # 2-frame roll, read-only outdir
  ✗ Error: f1.tiff: [Errno 13] Permission denied: '.../outdir/f1.tiff'
  ✗ Error: f2.tiff: [Errno 13] Permission denied: '.../outdir/f2.tiff'
  ```
  Every other user-facing error in this codebase is deliberately worded for a photographer
  (`ScanColorError` messages, the scan-exposure warnings, etc.) — this is the one class that falls
  straight through to Python's own errno text. For batch, the identical message repeats once per
  frame (2 of 2 here; would be 37 times on a real roll) even though it's the same one root cause.
- Requirement: brief's checklist ("error handling — is the message useful to a photographer?").
- Suggestion: (a) check `os.access(output_path.parent, os.W_OK)` (or a cheap `touch`-and-remove)
  before running the pipeline for a single file, so a bad output path fails in well under a
  second, not after a multi-second develop; (b) in batch, detect when every failure so far shares
  the same "can't write to the output directory" shape and stop early with one clear message
  instead of repeating it per frame (mirrors how `assess_roll`'s scan-consistency warnings are
  already deduplicated to one line — this is the same principle applied to write failures). S/M.
- Confidence: confirmed.

### 2.3-7: macOS AppleDouble sidecar files (`._IMG_0001.tif`) are not recognized as junk — they're queued as real jobs and reported as failures with raw tifffile text
- Severity: S3 UX friction
- Where: `src/halide/batch/orchestrator.py:159-169` (`discover_jobs` filters only by
  `.suffix.lower() in TIFF_SUFFIXES`, with no check for a leading `.` in the stem/name — the same
  gap exists in `cli/commands/contact_cmd.py:_collect`, which filters hidden `.DS_Store` etc. only
  incidentally via suffix, not by name).
- Evidence:
  ```
  $ ls mixedroll
  IMG_0001.tiff  IMG_0002.TIF  ._IMG_0001.tiff  corrupt.tiff  .DS_Store  snapshot.jpg  subfolder/
  $ halide batch mixedroll mixedout --rm ... --workers 1
  Roll   mixedroll · 4 frames → mixedout          # picked up 4, not the 2 real scans
  ...
  Completed with 2 failure(s) — 4/4 frames developed in 1.0s:
    ✗ ._IMG_0001.tiff: not a TIFF file: header=b'\x00\x05\x16\x07'
    ✗ corrupt.tiff: corrupted IFD structure
  exit=1
  ```
  `.DS_Store`, `snapshot.jpg`, and `subfolder/` were correctly excluded; uppercase `.TIF` was
  correctly included. Only the AppleDouble file is mishandled — and it's one of the most common
  things to find in a folder copied from/to a Mac (via a card reader, a network share, or a
  non-HFS+ drive), per the review's own Review Focus item 4. `corrupt.tiff` is arguably a correct
  failure (it's a real corrupt file the user should know about) but the message is tifffile's
  internal wording, not photographer language, and it still counts toward "failed" the same as the
  AppleDouble junk.
- Requirement: Review Focus item 4 ("expect them skipped with one clear line each, not a crash").
- Suggestion: Skip files whose name starts with `._` (and, generally, any dotfile) in
  `discover_jobs` and `contact_cmd._collect`, with one summary line ("skipped 1 macOS metadata
  file") rather than silently — the CLAUDE.md philosophy elsewhere is "skip and say so once," and
  this is exactly that case, just not yet applied here. S.
- Confidence: confirmed.

### 2.3-8: `_read_scan` treats any file tagged with halide's own output ICC profile as "already in the working space," so feeding an already-processed positive back into `invert`/`batch` re-applies density balance + tone curve silently instead of erroring
- Severity: S2 bug
- Where: `src/halide/processing.py:158-165` (`_read_scan`) — the fast path exists for the
  `halide print` round trip, but `process_scan`/`develop_request` never check that `stage` and
  "this file is already a positive" agree, unlike `print_scan` which explicitly checks
  `provenance.get("output") == "print"` and raises `PrintInputError` (`processing.py:608-613`).
- Evidence (read, not run to full corruption — the mechanism is directly visible in the code path):
  `invert`/`batch` have no equivalent guard to `print_scan`'s; a user who accidentally points
  `batch` at a folder that already holds halide output (e.g. re-running against `out/` instead of
  the original `roll/`, or a `--contact-sheet` preview folder mix-up) gets no `ScanColorError` and
  no warning — the pipeline runs to completion on data that's already a positive, invisibly
  compounding the tone curve and density balance a second time.
- Suggestion: `process_scan`/`develop_request` could check `read_provenance` the same way
  `print_scan` does and at least warn ("this looks like it's already a halide output, not a raw
  scan") before proceeding, for `stage is not Stage.INVERT_ONLY`. S/M.
- Confidence: likely (mechanism confirmed by code; not run against a real double-processed frame to
  see the visual result, which would need a real scan and is more a Task 4.3/5.1 concern than a
  processing.py code-path one).

### 2.3-9: `processing.py` (785 lines) and `orchestrator.py` (1037 lines) each mix two genuinely separable concerns
- Severity: S5 polish / code quality
- Where:
  - `processing.py:261-551` (roughly a third of the file) is entirely "how does this operation
    reach whichever device runs it" — `_shared_frame`, `_run_on_service`, `DeviceFailure`,
    `DeviceJobFailed`, `run_device_job`, `run_device_export`, `fall_back_to_cpu`,
    `export_fallback`, `_run_on_device` — used identically by `process_scan`, `print_scan`, and
    `export_delivery_image`, but conceptually distinct from "what happens to the pixels for this
    operation" (which is the other two-thirds: `_read_scan`/`_to_working_space`,
    `develop_request`/`print_request`/`export_request`, `_develop_in_place`).
  - `orchestrator.py:172-372` (the RAM/CPU worker-count estimator — `estimate_worker_memory_bytes`,
    `default_worker_count`, `memory_budget_warning`, and their export variants) and
    `orchestrator.py:408-608` (the GPU-service sizing/decision machinery — `shared_memory_worker_cap`,
    `estimate_service_host_bytes`, `batch_compute`, `service_worker_count`,
    `service_budget_warnings`) are both pure sizing math with no dependency on
    `ProcessPoolExecutor`/multiprocessing at all, sitting in the same file as the pool-running code
    (`_run_pool`, the four `_worker` functions) that does depend on it.
- Suggestion: Propose (not urgent) splitting `processing.py`'s device/fallback block into
  `processing_device.py` (or folding it into `device.py`, which already owns
  `ComputeDevice`/`resolve_device`), and `orchestrator.py`'s sizing math into `batch/sizing.py`.
  Both splits are mechanical (no behavior change, pure function relocation) and would cut each
  file by roughly a third, but the current single-file organization is still coherent and
  documented (each has a clear module docstring explaining what it does and why) — this is
  "would clearly help, moderate effort," not "currently confusing." M each.
- Confidence: likely (structural judgment call, not a defect).

## Checked, not a defect (for the synthesis pass)

- **Worker-count constants match CLAUDE.md exactly**: `_PEAK_RSS_MULTIPLIER = 3` /
  `_BASELINE_PROCESS_OVERHEAD_BYTES = 150 MiB` (develop), `_EXPORT_PEAK_RSS_MULTIPLIER = 2` /
  100 MiB (export), `_CUDA_CONTEXT_BYTES = 256 MiB`, `_DEVICE_FRAME_MULTIPLIER = 5`,
  `_GPU_HOST_OVERHEAD_BYTES = 1 GiB` — all as documented in CLAUDE.md's "Worker pool after that
  pass" and GPU sections. No drift found.
- **CPU batch never touches `/dev/shm`**: confirmed by code (`batch_compute` returns immediately
  for a non-GPU device without importing `halide.shared_frames`) and by a live run — `/dev/shm` was
  empty before and after a `--device cpu` batch (the two `sem.mp-*` semaphores seen during a run
  belong to Python's own `multiprocessing`, not `halide.shared_frames`, and disappear when the
  pool closes).
- **Ctrl-C during a CPU batch (mid-flight) and during the `--auto-density-roll` pre-pass are both
  clean**: process group vanished entirely after `SIGINT` (no orphaned workers/forkserver/
  resource-tracker left behind — verified with `ps --forest` on the batch's own PGID), exit code
  130, "⚠ Warning: Cancelled" (batch) / "Cancelled." (pre-pass, via `run_guarded`'s blanket
  `except KeyboardInterrupt`), no leftover `/dev/shm` segments, no leftover contact-sheet temp
  directory (`batch_cmd.py`'s `finally: shutil.rmtree(thumbnails, ...)` ran). Frames that had
  already finished writing before the interrupt were complete, valid files, not partial ones — the
  in-flight workers happened to be interrupted before reaching their own write step in every run
  tried; 2.3-3 shows the write step itself is not safe against exactly that timing, so this isn't a
  guarantee, just what was observed.
- **No cursor-hiding escape codes anywhere in `console.py`/`progress.py`** — so there's no
  "terminal left with a hidden cursor after Ctrl-C" failure mode to find; the progress display only
  ever writes cursor-up + clear-line, both idempotent.
- **Paths with spaces and non-ASCII characters** (`My Rólls (2026)/négatif один.tiff`) work
  cleanly through `invert` end to end.
- **Uppercase `.TIF`/`.TIFF`, hidden dotfiles other than `._*`, stray `.jpg`, and subfolders** are
  all handled correctly by `discover_jobs` (case-insensitive suffix match; subfolders never
  recursed into; non-TIFF suffixes excluded) — only the AppleDouble case (2.3-7) is mishandled.
